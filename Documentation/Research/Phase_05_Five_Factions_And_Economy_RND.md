**Проект:** GlobalFront — RTS по формуле C&C Generals / Zero Hour (Unity 6, dedicated server)
**Базовый коммит:** `34ce5ed` (1392 теста: 1370 EditMode + 22 PlayMode, 100% green)
**Дата:** 2026-11-03

Вторичная экономика: единый балансовый лимит строго 4 здания на игрока, единая цена $2000 и доход +$300/мин на здание (пик +$1200/мин у всех сторон), ноль спама и ноль микроконтроля |

| Очереди | Кольцевой буфер на 5 заказов из структур, продвижение таймера раз в тик, отмена = возврат 100%, ралли-поинт как авторитетный приказ при спавне |

## 1. Неизменяемые инварианты кодовой базы

Любое решение Фазы 5 обязано соблюдать следующие ограничения. Нарушение любого из них — автоматический откат спринта.

### И-1. Целочисленный детерминизм (авторитетное состояние)
- Тик 20 Гц, чистый C# в `GlobalFront.Core`, без Unity API.
- Координаты — `WorldPointMm` (int, миллиметры).
- В авторитетном состоянии **запрещены** `float`, `double`, `decimal`. Все вероятностные концепты заменяются детерминированными таблицами и таймерами. Случайных чисел в симуляции нет вообще (никакого `System.Random` в `GlobalFront.Core`).
- Деление — только целочисленное. Дробные коэффициенты выражаются парой `(числитель, знаменатель)` или пермилле (базис 1000). Округление при уроне — «половина вверх»: `(x * m + 500) / 1000`.
- Все ничьи (конкуренция за слот склада, выбор цели при равной дистанции) разрешаются **возрастанием `EntityId`** — единое правило на всю симуляцию.

### И-2. Строгий Zero-GC hot path
- В цикле тика, боевом резолвере, фильтрации репликации и сериализации снапшотов — `0 B GC.Alloc`.
- Все новые состояния — преаллоцированные массивы структур и кольцевые буферы фиксированной ёмкости. Запрещены: `List<T>`, `Dictionary<,>`, LINQ, боксинг, строки, замыкания, `foreach` по `IEnumerable`.
- Ёмкости фиксируются константами протокола (см. §10) и валидируются на старте матча.

### И-3. Авторитетный сервер и анти-чит
- Клиент шлёт только интенты; сервер валидирует каждый (гейты `MatchCommandRejection`).
- Данные о невидимых вражеских объектах не покидают сервер ни в каком канале (см. §8). Тест «оракула» — обязательный класс тестов Фазы 5: снапшот врага, снятый с фильтра, не должен содержать ни одного байта о невидимых для него сущностях, их здоровье, очередях, кредитах и факте строительства.

### И-4. Совместимость с 1392 тестами
- `UnitKinds` (`Unknown=0, Scout=1, Tank=2, BaseStructure=3, Count=4`) не расширяется и не переименовывается. Новые виды идут в отдельные каталоги (§2).
- Зарезервированные опкоды `Build=6, Produce=7, UseAbility=8` реализуются в `CommandWireCodec` с фиксированными полезными нагрузками (§5).
- Протокол снапшотов остаётся **protocol v2 с аддитивными записями**; существующие 40-байтные `DeltaAddRecord` и причины удаления не меняют смысла для юнитов.
- Плоские `Damage`/`MaximumHealth` в `CombatStats` сохраняются как базовые значения; матрица применяется поверх (§6).

## Раздел 1. Целочисленная детерминированная экономика (Resource & Supply Loop)

### 1.1. Модель сущностей

SupplyDock — склад снабжения на карте: конечный запас, слоты погрузки.
SupplyCenter — приёмный центр игрока: слоты разгрузки, точка привязки сборщиков.
Harvester — сборщик (один на фракцию, см. §7).
OilDerrick — захватываемая нейтральная вышка: пассивный доход.
SalvageCrate — обломок вражеской техники (только GLA).
SupplyDropCrate — сброс припасов (супособность США/НАТО).

Все сущности — структуры в преаллоцированных пулах:

| Пул | Ёмкость | Примечание |
|---|---|---|
| `SupplyDockPool` | 64 | Общие на матч |
| `SupplyCenterPool` | 20 | ≤ 4 на игрока × 4 игрока + запас |
| `HarvesterStatePool` | 64 | ≤ 16 на игрока |
| `OilDerrickPool` | 32 | |
| `SalvageCratePool` | 256 | Только GLA-смерти порождают записи |
| `SupplyEventRing` | 1024 | Кольцевой буфер событий цикла сбора |

### 1.2. Финансовые инварианты

- `Credits` — `int` на игрока, `0 ≤ Credits ≤ 1_000_000` (жёсткий потолок, защита от переполнения; начисления сверх потолка клампятся).
- Списание при заказе атомарно: `if (Credits < cost) → RejectInsufficientFunds` иначе `Credits -= cost`. Возврат при отмене — 100% (см. §5.3).
- Доходы всегда вида **«+N каждый K-й тик»**: `if (tickCounter >= period) { tickCounter -= period; credits += amount; }`. Никаких «в секунду», никаких дробей.

### 1.3. Цикл сбора (основная модель: США, Китай, Россия, НАТО)

Конечный автомат сборщика (`HarvesterCyclePhase`, byte):

Idle → ToDock → DockWait → Loading → ToCenter → CenterWait → Unloading → Idle

| Фаза | Правила |
|---|---|
| `ToDock` | Движение к назначенному складу. Склад выбирается сервером: ближайший (по квадрату дистанции в мм) склад с `RemainingSupply > 0`; ничья — меньший `EntityId`. Игрок может переопределить цель командой (интент сохраняется). |
| `DockWait` | Склад имеет `HarvestSlotCount` слотов (по умолчанию 4). Занятие слота атомарно в порядке прибытия, ничья по `EntityId`. Ожидание не потребляет ресурсов. |
| `Loading` | Таймер `LoadTicks` (фракционный, §7). По завершении: `cargo = min(CargoCapacity, RemainingSupply)`; `RemainingSupply -= cargo`. `cargo` — всегда целое. |
| `ToCenter` | Возврат к «своему» центру (закрепляется при спавне/покупке; переназначается командой). |
| `CenterWait` / `Unloading` | Слоты разгрузки центра (по умолчанию 2). **Разгрузка мгновенна** (1 тик) — как в оригинальной формуле: узким местом является погрузка и плечо маршрута. `Credits += cargo`. |

Гибель сборщика в любой фазе: груз утрачивается, `cargo` не возвращается никуда. Детерминировано.

Склад с `RemainingSupply == 0` помечается флагом `Depleted` (визуально — пустой, не участвует в выборе цели; сборщики в фазе `ToDock` перенаправляются на следующий склад в тот же тик).

### 1.4. Вторичные источники дохода (Сбалансированный стандарт: лимит 4 здания, единый темп)

Вторичная экономика приведена к строгому соревновательному паритету:
- **Единый лимит:** строго **до 4 зданий на игрока** (база остаётся военной крепостью, исключён спам десятков ферм).
- **Единая экономическая математика:** каждое здание стоит **$2000** и генерирует ровно **+$300 в минуту** (+$25 каждые 100 тиков / 5 сек).
- **Единый пиковый доход:** при постройке всех 4 зданий доход каждой фракции равен ровно **+$1200 в минуту** (окупаемость каждого здания ~6.5 минут).
- **Ноль микроконтроля:** здания работают автономно, ручные хакеры исключены.
- **Асимметрия** выражается в энергопотреблении, уязвимости и тактических свойствах:

| Фракция | Здание вторички | Лимит | Доход | Потребление энергии | Тактическая особенность фракции |
|---|---|---|---|---|---|
| **Китай** | **Дата-центр «Великая стена»** | 4 | +$300/мин (+$25 / 100 тиков) | -5 кВт (высокое) | Автоматические сервера без ручных хакеров. При блэкауте (Low Power) сервера гаснут (доход = 0). |
| **США** | **Зона логистики снабжения** | 4 | +$300/мин (+$25 / 100 тиков) | -3 кВт (умеренное) | Контейнеры с припасами материализуются на защищённой площадке (без уязвимых самолётов). Дополнительно даёт радар малого радиуса (20 м). |
| **GLA** | **Синдикат Чёрного рынка** | 4 | +$300/мин (+$25 / 100 тиков) | 0 кВт (автономия) | Работает **всегда** (у ГЛА нет электростанций, отключить блэкаутом невозможно). Но здание имеет лёгкую броню (уязвимо к артиллерии). |
| **Россия** | **Нефтеперерабатывающий терминал** | 4 | +$300/мин (+$25 / 100 тиков) | -6 кВт (очень высокое) | Здание обладает статусом `FortifiedStructure` (в 2 раза больше HP, тяжело снести диверсией или бомбардировкой). |
| **НАТО** | **Торгово-логистический хаб** | 4 | +$300/мин (+$25 / 100 тиков) | -3 кВт (умеренное) | В 1v1 работает штатно на себя. В 2v2 имеет переключатель: передавать 50% дохода в казну союзника при кризисе. |
| **Все** | **Нефтяная вышка (Нейтрал)** | 32 | +$500/мин (+$25 / 60 тиков) | 0 кВт | Нейтральный объект карты. Захватывается пехотой, даёт разовый стартовый бонус +$1000. Разрушаема. |

### 1.5. Приватность экономики (анти-чит)

- `Credits`, очередь заказов, `TechMask`, энергетические итоги **не являются полями снапшота мира**. Они доставляются отдельным владельческим каналом `PlayerLedgerUpdate` (надёжный, однонаправленный, только владелец и его союзники по команде — см. §8.3).
- Визуально враг может наблюдать **только** факт наличия здания и его прогресс достройки (когда здание видимо) — как в оригинальной формуле. Стоимость, оплаченность и очередь не передаются никому, кроме владельца.

### 1.6. Бюджет тестов раздела

~90 тестов: цикл сбора (все 6 фаз + ничьи + истощение склада), гибель в каждой фазе, вторичные источники, клампы, приватность (снапшот врага не содержит экономических полей — байт-в-байт), детерминизм (двойной прогон тик-в-тик, чексуммы совпадают).

## Раздел 2. Сетка строительства и энергосистема (Base Building & Power Grid)

### 2.1. Дискретный футпринт и сетка

- Каждое здание в каталоге `StructureKinds` имеет `FootprintMm` (ширина × глубина, кратные 500 мм) и `FootprintGridIndex` (индекс в преаллоцированной таблице масок ячеек футпринта — для проверки «любая ячейка видима», §8.2).
- Точка размещения — левый-нижний угол, выровненный по сетке **500 мм**: `snapped = (raw / 500) * 500`. Команда `Build` передаёт сырую точку; сервер сам выполняет снап — клиент и сервер всегда сходятся.
- Ориентация — 0..3 (шаг 90°), передаётся 2 битами; футпринт при 90/270° транспонируется.

### 2.2. Пять гейтов валидации размещения (порядок фиксирован)

1. **Границы карты:** весь футпринт внутри `[0, MapWidthMm] × [0, MapHeightMm]`. Иначе `RejectedOutOfBounds`.
2. **Строительная маска:** преаллоцированная `BuildabilityMask` (бит на ячейку 500 мм, строится один раз при загрузке карты из данных террейна): каждая ячейка под футпринтом обязана быть «строительной». Иначе `RejectedTerrain`.
3. **Перекрытие зданий:** AABB в мм против всех живых/строящихся структур (цикл по пулу структур, ≤ 512 записей; ранний выход). Иначе `RejectedOverlap`.
4. **Живые юниты:** ни одна точка живого юнита (любого владельца) не лежит внутри футпринта. Иначе `RejectedBlocked` (никаких «выталкиваний» — только запрет, это дешевле и детерминировано).
5. **Лимиты:** `structureCount < MaxStructuresPerMatch` и лимит зданий данного вида на игрока (напр., супероружие — 1). Иначе `RejectedLimit`.

Отдельно проверяется **существование и живость строителя** и оплата (`Credits >= cost`) до любого изменения мира.

### 2.3. Методы возведения и уязвимость строителей (Единое правило + фракционная асимметрия)

**Фундаментальное правило для ВСЕХ 5 фракций (включая ГЛА):**
- Любой строитель (бульдозер или рабочий) **смертен и может быть уничтожен врагом** в процессе стройки.
- Стройка продолжается **только пока строитель жив и находится на площадке**.
- **При гибели строителя стройка немедленно замораживается** на текущем проценте готовности (`BuildProgressTicks`) и текущем HP. Недостроенный каркас остаётся уязвимым на карте и может быть разрушен врагом.
- Чтобы возобновить строительство, игрок обязан прислать нового строителя и отдать команду достройки.

| Фракция | Строитель | Тип | Особенности и фракционная асимметрия |
|---|---|---|---|
| **США** | **Строительный дозер** | Техника | Быстрый, бронированный, автоматически тушит пожары и чинит соседние повреждённые здания в радиусе 15 м. |
| **Китай** | **Строительный дозер** | Техника | Бронированный; даёт скидку 10% на стоимость здания при возведении в радиусе 30 м от другого здания Китая (`cost = cost * 9 / 10`). |
| **GLA** | **Рабочий** | Пехота | Дешёвый, легко уязвим к снайперам и стрелковому оружию (`SmallArms`). **Уникальная механика мульти-стройки:** к одному зданию можно направить до 3 рабочих — каждый дополнительный рабочий ускоряет стройку (+50% к скорости за второго, +25% за третьего). При гибели одного рабочего темп падает, при гибели всех — стройка встаёт на паузу. |
| **Россия** | **Инженерная машина** | Тяжёлая техника | Высокий запас прочности (`HeavyVehicle`); при гибели оставляет обломки с 25% `SalvageValue` для любой стороны. |
| **НАТО** | **Строительный дрон** | БПЛА | Воздушный аппарат (игнорирует рельеф, высокая скорость перемещения между базами). Уязвим для огня зенитных комплексов (ПВО). |

Команда `Build` (опкод 6) несёт: `[builderEntityId:2][kindIndex:2][x:4][y:4][orientation:1] = 13 байт` полезной нагрузки.

### 2.4. Энергосистема

- Единица — условный кВт, `int16` в диапазоне `0..2000`. Каждое здание каталога задаёт `PowerProduced` и `PowerConsumed` (GLA: оба = 0).
- `PowerLedger` игрока хранит два кэшированных итога. **Пересчёт никогда не итерирует здания в тике**: любое событие (`StructureSpawned`, `StructureDestroyed`, `StructureSold`, апгрейд) применяет дельту ±значение из каталога. Стоимость — O(1).
- `DeltaP = PowerProduced − PowerConsumed`. Состояние `LowPower ⇔ DeltaP < 0` пересчитывается только в момент события.

**Детерминированные правила блэкаута** (применяются/снимаются в тот же тик, что и событие энергобаланса):

| Система | Эффект `LowPower` |
|---|---|
| Стационарная оборона (турели, ЗРК) | Не может стрелять (боевой резолвер пропускает цель; флаг `PoweredOff`) |
| Радары / сенсорные вышки / детекторы стелса | Детекция и бонусный обзор отключены |
| Очереди производства | Скорость ×2 медленнее: `if (lowPower && (currentTick & 1) != 0) — пропуск инкремента таймера` |
| Супероружие | Таймер кулдауна заморожен |
| Добыча | Не затрагивается (сборщики полевые) |

Репликация: флаг `PoweredOff` — 1 бит в записи структуры (§8.1); клиент рисует погасшее здание. Энергоитоги — только владельцу (§1.5).

## Раздел 3. Очереди производства и технологическое древо

### 3.1. Структура очереди (0 B GC)

```csharp
struct ProductionOrder {
    ushort ItemKindIndex; // индекс в каталоге юнитов/зданий-деплоя
    int TotalTicks;
    int RemainingTicks;
    int PaidCredits; // для 100% возврата
    byte Flags; // bit0: активен
}
// На здание:
ProductionOrder[] Slots = new ProductionOrder[5]; // кольцевой: head + count
```

- Продвигается только головной заказ: `head.RemainingTicks--` раз в тик (с учётом блэкаута, §2.4).
- По завершении: спавн юнита в `SpawnAnchorMm` здания (каталогная точка выхода, повёрнутая по ориентации) и немедленный авторитетный приказ движения на `RallyPointMm` здания (по умолчанию — точка выхода + 3 м наружу). Приказ оформляется тем же внутренним механизмом команд с синтетическим заголовком `PlayerId = владельца`, тик = текущий, что делает тракт единообразным.
- **Отмена** любого слота: возврат `PaidCredits` целиком, слот удаляется со сдвигом хвоста (≤ 4 сдвига структур копированием — без аллокаций).
- Переполнение (`count == 5`) → `RejectedQueueFull`.

Команда `Produce` (опкод 7): `[buildingEntityId:2][itemKindIndex:2][flags:1] = 5 байт`; `flags: 0 = поставить в очередь, 1 = отмена по индексу слота` (индекс — во втором байте `itemKindIndex` при отмене).

### 3.2. Точки сбора (Rally Points)

- Ралли ставится командой `UseAbility` (опкод 8, суб-команда `SetRally`) или неявно — при завершении строительства (точка выхода).
- Хранится на сервере в состоянии здания (`WorldPointMm`), реплицируется **только владельцу** (§8.3).
- Если ралли ведет в туман — это ответственность игрока; приказ исполняется авторитетно (движение в туман разрешено, как и любое движение).

### 3.3. Технологическое древо, ранги генерала и Правило Contra (Rank 3 Gate)

В GlobalFront вводится система боевого опыта генерала и строгое **Правило Contra (Rank 3 Gating)**, предотвращающее «быстрый пассивный выход в супероружие и Т3-технику» без активных боевых действий:

#### 3.3.1. Генеральский опыт и ранги (целочисленные)
- Опыт накапливается **только в боях**: при уничтожении любого вражеского юнита или здания игрок получает опыт, пропорциональный стоимости цели: `XP += TargetCost`.
- Ранги генерала (1..5 звёзд):
  - **Ранг 1 (1 Звезда):** 0 XP (старт игры, доступен T1);
  - **Ранг 2 (2 Звезды):** 1500 XP (доступен T2);
  - **Ранг 3 (3 Звезды):** 4500 XP — **Критический рубеж:** открывает доступ к постройке Т3-штаба (Стратегический центр, Дворец и т.д.);
  - **Ранг 4 (4 Звезды):** 9000 XP (элитные генеральские способности);
  - **Ранг 5 (5 Звёзд):** 16000 XP (супероружие и максимальные способности).

#### 3.3.2. Блокировка Стратегического центра до 3-го ранга
- **Стратегический центр (США), Стратегический штаб (Китай), Дворец (ГЛА), Инженерный штаб (Россия), Объединённый штаб (НАТО)** строго заблокированы, пока `PlayerState.Rank < 3`.
- Серверный валидатор `ValidateBuildCommand` немедленно отвергает попытку закладки: `if (structureKind.IsTier3Hub && player.Rank < 3) return MatchCommandRejection.InsufficientGeneralRank;`.
- Игрок **обязан** воевать юнитами 1-го и 2-го тира, зарабатывать фраги на карте и повышать ранг. «Голый фаст-тех» в бункере невозможен.

#### 3.3.3. Иерархия тиров

| Тир | Требование | Открывает | Примеры |
|---|---|---|---|
| **T1** | Ранг 1 + Стартовое КШ | Базовая пехота, сборщики, энергостанции | Рейнджеры, Рабочие, Электростанции |
| **T2** | Ранг 2 + Казарма/КШ | Основная бронетехника, легкое ПВО, аэродромы | Танки «Паладин»/«Битва-мастер», БТР, Хамви, МиГи |
| **T3** | **СТРОГО Ранг 3** + Завод | Стратегический центр, элитная техника, супероружие | Оверлорды, Объект 292, Протонная пушка, Ядерная ракета, СКАД-шторм |

## Раздел 4. Матрица типов брони и урона (целочисленная)

### 4.1. Классификация

**Броня (7):** `Infantry`, `HeavyInfantry`, `LightVehicle`, `HeavyVehicle`, `Aircraft`, `Structure`, `Fortified`.

**Урон (8):** `SmallArms`, `HeavyMachineGun`, `AntiTankCannon`, `GuidedMissile`, `ArtilleryExplosive`, `ThermobaricNapalm`, `ToxinChemical`, `HighTechLaser`.

### 4.2. Формула (единственная допустимая)

```csharp
long scaled = (long)baseDamage * multiplier; // переполнение исключено
int final = (int)((scaled + 500) / 1000); // округление «половина вверх»
final = Math.Max(final, baseDamage > 0 ? 1 : 0); // ненулевой урон не обнуляется
```

Опциональное плоское снижение (сверхтяжёлая броня России, ДОТы): вычитается **до** множителя: `base' = Math.Max(base - flatReduction, 1)`.

Матрица — `static readonly short[8 * 7]`, читается `DamageMatrix.Get(damageType, armorType)`. Никаких аллокаций, никакого боксинга.

### 4.3. Опорная матрица (базис 1000 = ×1.0; финальный тюнинг — OD-55)

| Урон ↓ / Броня → | Infantry | HeavyInf | LightVeh | HeavyVeh | Aircraft | Structure | Fortified |
|---|---|---|---|---|---|---|---|
| SmallArms | 1000 | 500 | 300 | 100 | 300 | 250 | 150 |
| HeavyMachineGun | 1200 | 600 | 500 | 150 | 400 | 300 | 200 |
| AntiTankCannon | 200 | 250 | 1000 | 1000 | 200 | 500 | 400 |
| GuidedMissile | 600 | 800 | 900 | 1200 | 1200 | 400 | 500 |
| ArtilleryExplosive | 1200 | 900 | 800 | 500 | 100 | 900 | 1000 |
| ThermobaricNapalm | 1500 | 1200 | 600 | 300 | 100 | 800 | 700 |
| ToxinChemical | 2500 | 1800 | 400 | 150 | 50 | 300 | 150 |
| HighTechLaser | 1000 | 1000 | 1000 | 1000 | 800 | 700 | 600 |

### 4.4. Расширения, заложенные в матричную модель

- **Сплэш** (артиллерия, термобарика): `SplashRadiusMm` + линейный целочисленный спад: `dmg(r) = base * (R − r) / R` (мм, целочисленное деление, `r < R`). Жертвы перебираются по сетке видимости (та же uniform grid), порядок — возрастание `EntityId`.
- **ДоТ горения** (напалм): `BurningTicks` + `BurnDamagePerPeriod` (целые), счётчик на жертве, без аллокаций.
- **Токсины и вытравливание гарнизонов (ГЛА)** (`ToxinChemical`):
  - *Вытравливание (Garrison Cleanse):* при попадании в занятое здание урон транслируется находящейся внутри пехоте с множителем `Infantry` (выкуривание пехоты из зданий без сноса стен — прямо как в Generals).
  - *Зона заражения (Toxic Contamination Field):* Токсичный трактор и ракеты СКАД оставляют на земле детерминированную область радиуса `HazardRadiusMm` на `HazardDurationTicks`, наносящую периодический урон `ToxinChemical` всем наземным юнитам внутри.
  - *Кислотное разъедание (Anthrax Gamma / Тракс):* апгрейд модифицирует множители против `LightVehicle` (до 800) и `HeavyVehicle` (до 600) — кислота растворяет броню.
- **Эскалация Гатлинга** (Китай): уровень 0..3 по непрерывному огню (`ChargeTicks` растёт, сбрасывается после 40 тиков тишины); пороги 20/60/120 тиков дают множители 1000/1400/1800/2200 к базовому урону оружия.
- **Стан** (ЭМП НАТО): `StunTicks` — цель не двигается и не стреляет; обратный отсчёт целочисленный.

### 4.5. Обратная совместимость (критично для 1392 тестов)

`CombatStats` получает поля `DamageType` и `ArmorType` типа `byte` с **сентинелом 255 = «легаси»**. Если у атакующего ИЛИ цели сентинел — применяется старое плоское поведение (`final = baseDamage`, как сегодня). Все существующие `Scout`/`Tank`/`BaseStructure` остаются на сентинеле до шага 5.5, где им назначаются реальные типы отдельным коммитом с контролируемым обновлением ожиданий. Таким образом шаги 5.1–5.4 **не способны** изменить поведение существующих тестов.

### 4.6. Бюджет тестов раздела

~65 тестов: вся матрица 8×7 на опорных значениях, округление на границах (×999, ×1001, нечетные произведения), плоское снижение, сплэш-спад, ДоТ, вытравливание гарнизонов, эскалация, легаси-сентинел (бит-в-бит со старым поведением).

**Супособности:** Минное поле (временные мины 600 тиков), Окопная сеть (пехота в зоне получает `Fortified`-множитель 600 тиков).

### 5.5. НАТО — «Единое поле и горизонт»

**Доктрина:** коалиционная точность; сенсорная сеть; разведка и дальний огонь; синергия с союзником (фракция «заточена» под 2v2). Средняя стоимость, высокая информированность.

**Уникальные механики:**
1. **Единое тактическое поле:** Сенсорная вышка даёт детекцию стелса 35 м и +10 м обзора союзным юнитам в радиусе 60 м (бонус применяется на тике видимости, целочисленно). В 2v2 вышки НАТО обслуживают всю команду через Shared Vision (§9).
2. **Загоризонтная наводка:** артиллерия НАТО получает дальность ×3/2, **если цель видима командной маской, но не видима самому стрелку**. Сервер проверяет условие в момент выстрела: `targetVisibleForTeam && !targetVisibleForSelf` (§9.2).
3. **Воздушная логистика дронами:** сборщик-беспилотник (малый груз, быстрый, воздушный).
4. **ЭМП-доктрина:** супероружие отключает технику и энергозависимые здания противника.

**Здания:** КШ «Совместное командование», Энергоузел (+11), Кадровый центр, Казарма, Логистический хаб, Механизированный завод, Аэрокрыло, Объединённый штаб (T3), Сенсорная вышка (уникальная), Самоходная гаубичная батарея (здание-артиллерия, загоризонтная).
**Пехота:** Егеря (дальние `SmallArms`), Оператор ПТУР, Разведчик-корректировщик (расширяет обзор команды на 15 м в точке — «маяк наводки»), Инженер НАТО (ремонт техники в поле), Снайпер «Тень».
**Техника:** «Феннек» (разведчик, быстрый), «Боксер» БТР (перевозка 6), «Леопард 2А7» (средний+), Истребитель танков «Центавр», САУ ПзХ-2000 (загоризонтная), ЗРК «Пэтриот-Е», Ремонтная машина.
**Авиация:** «Еврофайтер» (перехватчик), Вертолёт «Тигр», Дрон-жнец (разведка/удар).
**Супероружие:** **ЭМП «Затмение»** (радиус 30 м: вся вражеская техника и энергозависимые здания получают стан 600 тиков; пехота не затронута; кулдаун 12000, $4500).
**Супособности:** Сброс припасов (общая с США), Дымовая завеса (зона, где снаряды наведения теряют цель 400 тиков).

### 5.6. Общие подсистемы асимметрии (реализуются один раз)

- **Ауры** (орда, пропаганда, комиссар, корректировщик): применяются раз в `AuraPeriodTicks = 20` через обход сетки 8192 мм вокруг источника; лимит целей на ауру (16); порядок применения — возрастание `EntityId` источника, затем цели. Бюджет: ≤ 32 аур на матч, ≤ 512 проверок ячеек на тик ауры суммарно.
- **Стелс и детекция:** юнит со флагом `Stealth` невидим врагам, пока не попал в радиус детектора (здание-детектор, башня, дрон). Расширение `VisibilityEngine`: для стелс-юнитов видимость = пересечение «обычной» видимости и маски детекторов врага. Детерминировано, без аллокаций (преаллоцированный список детекторов на команду, ≤ 64).
- **Захват вышек / угон (ГЛА):** единый механизм канала `CaptureChannel`: пехота вплотную к цели, таймер, прерывается уроном. Только нейтральные вышки (все) и вражеская техника (только Угонщик ГЛА).

## Раздел 6. Сетевой протокол и Anti-Cheat тумана войны

### 6.1. Структуры в дельта-снапшотах

Протокол остаётся **v2, аддитивным**. Вводятся две новые записи (старые опкоды и 40-байтный `DeltaAddRecord` юнитов не изменяются):

**`StructureAddRecord` — фиксированные 48 байт:**

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 2 | `RecordOpcode = 0x07` |
| 2 | 2 | `EntityId` (ushort) |
| 4 | 4 | `V_tick` (uint) |
| 8 | 2 | `StructureKindIndex` |
| 10 | 1 | `OwnerPlayerId` |
| 11 | 1 | `Flags` (bit0 `UnderConstruction`, bit1 `PoweredOff`, bit2 `GarrisonFull`, bit3 `DepletedDock`) |
| 12 | 8 | `PositionMm` (X/Y int32) |
| 20 | 1 | `Orientation` (0..3) + резерв |
| 21 | 2 | `BuildProgress` (пермилле 0..1000) |
| 23 | 4 | `Health` (int32) |
| 27 | 16 | Резерв под дельта-поля (гарнизон-маска, спец-состояния) |
| 43 | 5 | Выравнивание |

**`StructureUpdate`** — дельта по тем же правилам, что и для юнитов (переходы `V_base → V_cur`, слияние `1→1`, фолбэк на кейфрейм при `encodedSize > MaxPayloadBytes`).

Удаление структуры в туман использует существующий формат REMOVE с новой причиной: `RemoveReason.GoneDark = 2` (юниты продолжают использовать `FogOfWarHidden = 0` / `Destroyed = 1` — поведение существующих клиентов и тестов не меняется).

### 6.2. Разведанный туман и «призрак» последнего известного состояния

- Когда структура переходит `1→0` в маске клиента, сервер шлёт REMOVE с причиной `GoneDark`. Клиент **не удаляет** представление, а переводит его в режим «призрак»: последний известный `Health`, `BuildProgress`, позиция — затемнённая модель, некликабельная как источник данных.
- Когда структура возвращается `0→1`, сервер шлёт полный `StructureAddRecord` с **текущим** состоянием (не с «призрачным») — клиент мгновенно обновляет модель.
- Структура, построенная в зоне, которую игрок **никогда** не видел, не попадает в его снапшоты вообще (фильтр никогда не фиксировал переход в 1). Это фундаментальное свойство: `GoneDark` генерируется только для записей, ранее бывших видимыми.
- Клиентская симуляция «призраков» запрещена: никакой локальной экстраполяции вражеской экономики. Призрак — чисто презентационный объект из последнего снапшота.

### 6.3. Видимость структур

- Структура видима клиенту, если **любая** ячейка её футпринта (преаллоцированный список ячеек из каталога, ≤ 16 ячеек) видима в маске игрока. Проверка — `Or` масок ячеек, без аллокаций.
- Строящиеся структуры (`UnderConstruction`) видимы по тем же правилам (факт стройки — легитимная разведданные, как в оригинальной формуле).

### 6.4. Владельческий приватный канал (`PlayerLedgerUpdate`)

Надёжный однонаправленный канал поверх транспорта (аналогично `SessionSecretMessage`), отправляется **только при изменении** (не каждый тик):

```text
[opcode 0x15:1][recipientMask:2][playerId:1]
[credits:4][powerProduced:2][powerConsumed:2]
[techMaskLo:8][techMaskHi:8]
[queueEntries: N × (buildingEntityId:2, slotCount:1)] // сводка очередей, ≤ 20 зданий
```

`recipientMask` — получатели: владелец и его команда. Вражеская команда не получает запись никогда. Бюджет трафика: десятки байт на событие изменения.

### 6.5. Чексуммы

- Существующая per-client `StateChecksum` (FNV-1a по видимому срезу) расширяется на записи структур в том же порядке (`EntityId` по возрастанию).
- Для владельческого канала вводится отдельная `LedgerChecksum` (только владелец; союзники получают отображаемые значения без права сверки — упрощает паритетные тесты).
- В 2v2 обе команды имеют разный видимый срез → разные чексуммы легитимны; тесты паритета сверяют чексуммы **внутри** команды.

### 6.6. Оракульные тесты (обязательный класс)

Для каждого нового типа данных — тест: «снять дамп дельт для врага, не имеющего видимости зоны, и побайтово убедиться в отсутствии записей». Покрыть: факт постройки, здоровье/прогресс, кредиты, очередь, ралли, истощение склада, содержимое туннелей (юниты внутри туннеля невидимы всем, кроме владельца).

### 6.7. Бюджет тестов раздела

~70 тестов: кодек новых записей (прямой/обратный, выравнивание 48 байт), `GoneDark`-циклы, призрак не содержит будущих данных, оракульные дампы, `PlayerLedgerUpdate` адресация, чексуммы.

## Раздел 7. Топология 2v2 (Milestone M2, OD-48)

### 7.1. Конфигурация матча

- 4 слота игроков: команда = `slot / 2` (слоты 0–1 = команда 0, 2–3 = команда 1); лобби может перемешивать составы до старта — топология хранится в `MatchTopology2v2` (уже существует в Core).
- `DedicatedServerRunner` собирает `ServerHost` с `Team2v2CombatRelation` и вызывает `SetPlayerTeam` для всех четырёх игроков на старте. Это прямо закрывает OPEN-бэклог: «`Team2v2CombatRelation` и `SetPlayerTeam` не подключены runtime-композицией».
- `BitMask1024` уже рассчитана на 10 игроков — протокол игрока не меняется; меняется только серверная политика видимости и боевой резолвер.

### 7.2. Shared Vision (общий туман войны команды)

- На каждый тик репликации сервер один раз вычисляет **командные маски**: `TeamMask[team] = OR масок всех живых игроков команды` (для `BitMask1024` — операция `Or` над 16×ulong, ≤ 2 операции на команду, преаллоцированный скретч — 0 аллокаций).
- Пер-клиентная фильтрация использует `TeamMask[teamOf(client)]` вместо персональной маски. Следствие: оба союзника получают **идентичный** видимый срез — это упрощает чексуммы, дебаг и паритетные тесты.
- Командная маска применяется в трёх местах:
  1. `FogOfWarReplicationFilter` (что попадает в снапшот);
  2. фо́говый гейт атаки `TryEnqueueAttack` (цель видима **команде** — легитимный огонь по метке союзника; расширяет существующий гейт шага 4.4.1 без смены его структуры);
  3. загоризонтное условие НАТО (§5.5): `teamVisible && !selfVisible`.
- Личные ресурсы/очереди в Shared Vision **не входят** (§6.4).

### 7.3. Дружественный огонь и командная победа

- `Team2v2CombatRelation.IsHostile(a, b) == false` внутри команды → существующее подавление дружественного огня (спринт 1.3) работает без изменений; добавляются интеграционные тесты на 4 игроков.
- Победа: у **обеих** игроков вражеской команды не осталось юнитов и структур → командная победа (расширение существующего `team victory outcome` на структуры — структуры становятся учитываемыми сущностями исхода).
- Ничья не предусмотрена: матч идёт до уничтожения.

### 7.4. Пауза, реконнект и покидание в 2v2

- Тактическая пауза: возобновление по **кворуму** — `ClientReadyToResume` (C0, опкод 14) получен от всех подключённых сессий, либо истёк грайс-период (4000 тиков, как в M1).
- Покинувший игрок считается `Abandoned` после таймаута реконнекта; его юниты/здания остаются в мире (не управляются), союзник продолжает игру. Команда, потерявшая все 4 сессии (2 игрока × исчерпанные реконнекты) — поражение по неявке.
- Ресинк после реконнекта уже покрывает структуры бесплатно: кейфрейм расширен структурной секцией (§6.1), `KeyframeInstalled` → `HandleResync` без изменений.

### 7.5. Бюджет тестов раздела

~60 тестов: композиция 2v2 в раннере, `SetPlayerTeam` на 4 слота, Shared Vision (маска команды, идентичность срезов союзников, изоляция врага), командный фо́говый гейт атаки, подавление дружественного огня в 4 игрока, командная победа (включая структуры), пауза-кворум, реконнект 1 из 4 под потерями, поражение по неявке.

## Раздел 8. Декомпозиция Фазы 5: шаги 5.1–5.6 и критерии приёмки

Общие правила для всех шагов (Definition of Done каждого):
1. Все существовавшие тесты зелёные **до** и **после** шага (никаких «временно красных» веток).
2. `0 compiler warnings, 0 compiler errors`.
3. Zero-GC гейт: скоупированное окно (транспорт + репликация, презентация отключена) — 0 блоков; замер тика симуляции в гардах (400 юнитов ≤ 8.0 мс; бюджет видимости с учётом структур ≤ 1.2 мс).
4. Bite-прогон revert-to-fail для каждого наблюдаемого фикс-поведения.
5. Коммит атомарный; документация (фаза-файл, ADR, OD) обновлена в том же коммите.

### Шаг 5.1 — Матрица урона/брони (фундамент)
**Скоуп:** `DamageType`/`ArmorType`, матрица 8×7 (включая `ToxinChemical` ГЛА), формула §4.2, плоское снижение, легаси-сентинел 255, расширение `CombatStats`.
