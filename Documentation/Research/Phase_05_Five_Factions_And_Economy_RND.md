## 1. Целочисленная детерминированная экономика (Resource & Supply Loop)

### 1.1 Модель ресурсов и единицы измерения

Авторитетное состояние игрока (все поля целые, ни одного вещественного):

| Поле | Тип | Семантика |
|---|---|---|
| `Credits` | `int` | Баланс игрока. Начисление только сервером; клиент получает копию по приватному каналу (§1.5). Верхняя граница `MaxCredits = 2_000_000_000` — сатурация при начислении (без overflow) |
| `TechMask` | `ulong` | Битовая маска разблокированных технологий (§3.5) |
| `BuildingKindsMask` | `ulong` | Маска построенных видов зданий (для техтребований «нужна казарма») |
| `PowerProduced` / `PowerConsumed` | `int` | Агрегаты энергосети (§2.4), пересчитываются по составу зданий |
| `LowPower` | `bool` (int-флаг) | ΔP < 0 (§2.4) |

Запасы на карте — целые сущности:

- `SupplyDock` — конечный запас: `RemainingDollars` (`int`, проект 30 000 на старте), слоты погрузки — фиксированный преаллоцированный массив `Slot[4]` (занятый `EntityId`, 0 = свободен).
- `SupplyCenter` — точка мгновенной разгрузки.
- Сборщик — сущность-юнит с грузом `CarriedDollars` (`int`, 0…`CapacityDollars`).

Все цены, выработки и начисления — целые доллары; все задержки — целые тики (20 Гц).

### 1.2 Цикл сбора: детерминированный FSM на тиках

Сборщик живёт в FSM, каждая дуга — чистая функция от тика и целого состояния (никакого стенного времени):

```
Idle → ToDock → WaitSlot → Loading(LoadTicks) → ToCenter → Unload(0 тиков) → ToDock → …
```

1. **ToDock** — движение к точке слота целевого склада существующим `PlanarMovement.StepTowards` (`Runtime\Core\PlanarMovement.cs`), скорость из архетипа. Выбор склада: ближайший с `RemainingDollars > 0`; равенство дистанций → меньший `EntityId` (канонический порядок — детерминизм).
2. **WaitSlot** — если все `Slot[4]` заняты, сборщик стоит в очереди у склада. Освободившийся слот получает **первый по (времени прибытия, EntityId)** ожидающий — очередь упорядочена, аллокаций нет (массив `waiting[MaxHarvestersPerDock]`, уплотнение сдвигом).
3. **Loading** — ровно `LoadTicks` (проект: 40 тиков = 2 с). По завершении атомарно: `take = min(LoadCapacity, RemainingDollars, CapacityDollars - CarriedDollars)`; `RemainingDollars -= take; CarriedDollars += take`. Сборщик берёт ровно `LoadCapacity` (проект 300; Chinook США — 600), если запас позволяет.
4. **ToCenter** — движение к ближайшему своему `SupplyCenter` (их можно строить несколько; при равенстве дистанции — меньший `EntityId`, канонический выбор).
5. **Unload** — в тик прибытия: `Credits = saturatingAdd(Credits, CarriedDollars)`; `CarriedDollars = 0`; счётчик `StatisticsHarvested += cargo` (текущий счётчик идёт в реплей/логи, не в игровое состояние). Мгновенность по ТЗ.

Расход на производство/стройку списывается в тик принятия заказа (§3.4): `Credits >= cost` проверяется атомарно с вычитанием — никаких «в долг».

### 1.3 Вторичные источники (целые таймеры, никакого «в секунду» с вещественной долей)

Каждый источник — накопитель с целым периодом в тиках:

| Источник | Кому | Механика | Проект параметров |
|---|---|---|---|
| Oil Derrick | Всем | Нейтральное здание, захват пехотой (§1.4). Пока владелец есть: `+OilIncome` каждые `OilPeriodTicks` | +100 $ / 40 тиков (2 с) |
| Hacker | China | Юнит; пока жив и не в бою — `+HackerIncome` каждые `HackerPeriodTicks`; бездействие проверяется флагом «не стрелял N тиков» | +20 $ / 40 тиков |
| Black Market | GLA | Здание; пока живо — `+MarketIncome` каждые `MarketPeriodTicks` | +50 $ / 80 тиков |
| Supply Drop Zone | USA | Здание; пока живо — `+DropValue` каждые `DropPeriodTicks` (детерминированное расписание от тика постройки) | +1500 $ / 1200 тиков (60 с) |
| Обычный цикл | Russia, NATO | только SupplyDock/SupplyCenter + Oil Derrick (без уникального вторичного источника — доктринная компенсация в §5.4/§5.5) | — |

Все накопители — счётчики `ticksSinceLastPayout` в преаллоцированном состоянии здания/юнита; выплата в фазе экономики тика (§1.6). Детерминизм: период считается от тика постройки/захвата, а не от «wall clock».

### 1.4 Захват нейтральных экономических зданий (минимальный, без полного garrison)

Полный гарнизон/захват — заявленная в GDD механика 1.0, но **не в скоупе Phase 5** (ТЗ требует только нефтяные вышки как источник). Минимальная версия, чтобы цикл Oil Derrick работал:

- Пехота (и только пехота) может получить приказ `Attack` на нейтральное здание → вместо урона идёт оккупация: `OccupationTicks` (проект 80 тиков = 4 с) непрерывного нахождения внутри футпринта.
- Срыв: юнит получил урон или ушёл из футпринта → счётчик сбрасывается.
- Завершение: владелец меняется атомарно; выплаты идут новому владельцу.
- Конкурентный захват: счётчик один на здание, считается последним оккупантом (правило: пересчёт от текущего оккупанта; детерминизм — счётчик принадлежит зданию, а не юниту).

Граница скоупа фиксируется в DoD Шага 5.2: полный garrison (стрельба из зданий, вместимость по типу юнита) — отдельная система за Phase 5.

### 1.5 Приватность экономики: строго владельцу (защита от мапхака)

`Credits`, `TechMask`, состав очередей, `PowerProduced/Consumed`, `LowPower` — **приватные данные владельца**. Они не могут ехать в общий C2-поток дельт (его фильтрует FoW, но он в принципе адресован «видимому миру»). Решение — отдельный надёжный приватный канал:

- Новый `TransportMessageType.PlayerStateSync = 15` (следующий свободный после `ClientReadyToResume = 14`, `TransportProtocol.cs:26-51`) — **per-session**, reliable (канал C0/C1), отправляется **только владельцу** при изменении состояния и keepalive-дайджестом раз в `IdleKeepAliveTicks` (20 тиков).
- Полезная нагрузка — абсолютное состояние (не дельта): `[version u8][tick u64][credits i32][techMask u64][buildingKindsMask u64][powerProduced i32][powerConsumed i32][lowPower u8][queueDigest…]`. Потеря пакета лечится следующим дайджестом — идемпотентно, latest-wins, не требует ACK-машинерии поверх C0.
- Очереди производства: компактный дайджест «здание → 5 слотов × (blueprintId u16, remainingTicks u16)» (≤ 5 × 5 × 4 = 100 B + идентификаторы). Верхняя оценка трафика: ≤ 128 B × 10 Гц = 1.3 KB/s на игрока — пренебрежимо против pacing 40 960 B/s.
- Запасы складов (`RemainingDollars`) — **публичны**: склад стоит на карте, его состояние видно разведкой, поэтому оно реплицируется обычным путём как поле сущности (§6.2, поле `AuxState`).
- Союзники **не** получают приватные данные друг друга (ТЗ: «строго своему владельцу»). Team-shared экономика — TBD post-1.0.
- Чексумма: приватный слой не входит в per-client `StateChecksum` отфильтрованного среза (срезы у разных клиентов различаются по построению, OD-40). Расхождение приватного состояния ловится реактивно: неверный баланс приводит к отклонению Build/Produce команд (`InsufficientFunds`) и виден в логах. Прямая сверка приватного слоя — открытый вопрос (§9).

### 1.6 Интеграция в тик, Zero-GC и детерминизм

- Новая фаза тика `AdvanceEconomy` вставляется в `MatchServer.TickOnce` (`:696-718`) **после** `AcquireAutomaticTargets` и **до** `MoveUnits`: начисления вторичных источников и снятие грузов происходят до движения — порядок фиксирован и документируется как protocol-significant (любая перестановка фаз меняет траекторию десинков).
- FSM сборщиков продвигается в той же фазе (`StepHarvesters`): переходы — чистые функции от тика; перебор по `_orderedUnits` в каноническом порядке `EntityId` — результат не зависит от порядка хранения.
- Zero-GC: всё состояние — массивы фиксированной ёмкости (`PlayerEconomyState[MaxPlayers+1]`, `Slot[4]` на склад, `waiting[]` на очередь слота, накопители в архетипных записях). Никаких `List`/LINQ/замыканий на горячем пути; уплотнение очередей — сдвиг в преаллоцированном массиве.
- Целочисленность: все начисления `int`, сатурация на `MaxCredits`; все периоды — тики; ни одной вещественной дроби (никаких «$2.5/сек»).

### 1.7 Тесты раздела (DoD-фрагмент)

1. Детерминизм: два прогона одного сценария (2 склада, 3 сборщика, 2000 тиков) дают бит-равные `StateChecksum` и бит-равные `Credits`.
2. Очередь слота: канонический порядок (время прибытия, `EntityId`) воспроизводится при любой перестановке спавна.
3. Истощение склада: при `RemainingDollars < LoadCapacity` берётся остаток; склад с 0 не выбирается целью.
4. Сатурация: `Credits` у `MaxCredits` не переполняется при разгрузке.
5. Изоляция: клиент B ни на одном тике не получает `PlayerStateSync` игрока A; видимость `RemainingDollars` вражеского склада закрыта туманом.
6. Захват Oil Derrick: срыв при уроне; выплата только текущему владельцу.
7. Zero-GC: `Is.Not.AllocatingGCMemory()` на 2000 тиков с активной экономикой; гейты инвариантов архитектуры зелёные.

## 2. Сетка строительства и энергосистема (Base Building & Power Grid)

### 2.1 Дискретный футпринт и строительная сетка

- `BuildingGridCellMm = 10_000` (10 м). Здание занимает `W × H` целых ячеек; позиция здания = (мировые мм, юго-западный угол) + размеры в ячейках из архетипа.
- `FootprintMm` здания = `W × BuildingGridCellMm × H × BuildingGridCellMm` — целая величина, производная от ячеек; никакой плавающей геометрии.
- Занятость сетки: `int[] BuildingOccupancy[mapCells]` — значение = `EntityId` здания (0 = свободно), преаллоцировано по размеру карты. Для стандартной карты 400×400 м (домен миникарты OD-27, ±200 000 мм) это 40×40 = 1600 ячеек — тривиально; для больших карт — та же сетка от `MapBounds`.
- Карта Phase 5: продолжает использоваться карта-плейсхолдер Phase 3/4 (400×400 м, ровный террейн). Пассабильность террейна — маска `impassable[cell]` из данных карты (в Phase 5 заполняется 0 — террейн не добавляется; формат готов для Phase 7).

### 2.2 Размещение зданий: валидация в фиксированном порядке

`Build`-команда (opcode 6) несёт: `builder EntityId (0 для модульного метода)`, `blueprintId u16`, `originCell (i16,i16)`. Сервер проверяет **в фиксированном порядке** (первое нарушение — отказ, каждый отказ — отдельный `MatchCommandRejection`-код, добавление после `TargetInFogOfWar=12`):

1. `MapBoundsViolation` — футпринт целиком внутри карты.
2. `TerrainImpassable` — ни одна ячейка футпринта не помечена impassable.
3. `BuildingOverlap` — все ячейки футпринта свободны в `BuildingOccupancy`.
4. `UnitInsideFootprint` — свои юниты внутри футпринта получают **авторитетный приказ покинуть** футпринт (детерминированное смещение к ближайшей свободной ячейке по спиральному каноническому порядку); юниты противника/нейтралов внутри — отказ `EnemyUnitBlocking`.
5. `TechNotUnlocked` / `InsufficientFunds` — маска техтребований (§3.5) и списание стоимости.
6. Опционально (Owner Decision): запрет строительства в радиусе `EnemyBuildExclusionMm` от вражеских зданий (Generals-правило); в Phase 5 по умолчанию **отключено** — формула не требует.

Проверка видимости: стройка в **неразведанной** зоне разрешена, если у игрока есть разведанность ячейки (Explored-карта клиента — презентационное понятие; серверный эквивалент: ячейка была в маске видимости игрока хотя бы на одном тике — `ExploredCells[player]` битовая карта ячеек, обновляется в фазе видимости; преаллоцирована, Zero-GC). Стройка вслепую (в туман без разведки) — отказ `NotExplored`. Это и анти-мапхак: сервер не подтверждает «слепую» разведку геометрии карты через отказы стройки.

### 2.3 Методы возведения: одна модель, три интерфейса

Единая модель: `Build` создаёт сущность **финального архетипа сразу** с `BuildProgressMilli = 0` — здание «поднимается», как в Generals. Это осознанный протокольный выбор: архетип не меняется in-place (инвариант OD-29: «an archetype never changes in place», `Runtime\Core\Snapshot\DeltaSnapshotModel.cs` — сущность с рождения несёт финальный `BlueprintId`/`UnitKind`), а `EntityId` не рвётся. Поля записи: `OriginCell, BuildProgressMilli (0…1000), BuilderEntity (0 = модульный), PaidCost`.

Пока `BuildProgressMilli < 1000` здание **неактивно**: не стреляет, не производит, не принимает заказы, не даёт `PowerDelta` и не является источником обзора. Продвижение — в фазе `AdvanceConstruction` тика:

- **Dozer (USA/China):** `Build` создаёт здание-каркас и выдаёт дозеру авторитетный приказ к нему. Пока дозер в радиусе `BuildWorkRadiusMm` и жив: `BuildProgressMilli += BuildWorkPerTick` (проект 25/тик; полные времена — в архетипах §5). Дозер, получивший урон, продолжает (Generals-правило: стройка не срывается уроном строителю).
- **Worker (GLA):** тот же контракт, дёшев, один юнит строит любое здание.
- **Модули (Russia/NATO):** `BuilderEntity = 0` — модуль-надстройка: `BuildProgressMilli` растёт сам, пока живо опорное здание и нет LowPower (§2.4). Нет юнита-строителя → нет уязвимого дозера, но стройка останавливается при потере опоры/питания. Стоимость списывается сразу при создании.

Завершение: `BuildProgressMilli >= 1000` — в тот же тик здание становится активным (переход состояния, не roster-переход). Отмена до завершения — возврат 100% (консистентно с §3.4) и REMOVE.

Каркас появляется в видимости противника только если в его маске (FoW-фильтр уже это обеспечивает — каркас это сущность; §6.4); степень готовности реплицируется полем `BuildProgress` (§6.2).

### 2.4 Энергосеть: ΔP и детерминированные правила LowPower

- Каждое здание (архетип) несёт `PowerDelta` (`int`): выработка > 0, потребление < 0. GLA: все здания `PowerDelta = 0` (доктрина «0 потребности в энергии» — сеть для GLA просто не считается).
- Агрегаты `PowerProduced/PowerConsumed` игрока пересчитываются **только** при изменении состава/состояния его зданий (кэш; пересчёт — один линейный проход по своим зданиям в фазе строительства, не каждый тик).
- `LowPower = PowerProduced - PowerConsumed < 0`. Правила (все детерминированные, целые):
  1. Стационарная защита — **офлайн**: не проходит `CanFire` (серверный флаг питания в записи здания).
  2. Радар — офлайн: радарные здания (Radar Station, Satellite Uplink, Sensor Array) перестают быть источниками обзора (радиус 0 при LowPower; требует пер-юнитного радиуса §6.6); накопленная разведанность (Explored, §2.2) остаётся.
  3. Очереди производства — **вдвое медленнее**: прогресс тикает базисом 1000, при LowPower добавляется 500 за тик вместо 1000 (целое, без дробей).
  4. Модульная стройка Russia/NATO — останавливается (п. 2.3); стройка дозером/воркером — не останавливается (Generals-правило: строитель автономен).
  5. Сборщики — не затрагиваются (по Generals-формуле).
- Переход LowPower ↔ Normal мгновенный и симметричный по ΔP; гистерезис не нужен (целочисленно нет осцилляций на границе, т.к. ΔP — целая величина и меняется только событийно).

### 2.5 Репликация стройки и Zero-GC

- Каркас/здание — одна и та же сущность с рождения (§2.3): реплицируется существующим дельта-путем (ADD/UPDATE/REMOVE, §6). Прогресс стройки виден разведке как поле `BuildProgress` (basis 1000) — честный аналог Generals (противник видит степень готовности, только разведав каркас).
- `BuildingOccupancy`, `ExploredCells`, кэш энергосети, очереди — преаллоцированы при старте матча; фазы строительства не аллоцируют.
- Требование целочисленности: все координаты/размеры в мм и ячейках, весь прогресс в милли-базисах.

### 2.6 Тесты раздела (DoD-фрагмент)

1. Валидация в фиксированном порядке: по одному кейсу на каждый отказ (граница, террейн, перекрытие, юнит-блокер, технология, деньги, неразведанность).
2. Дозер/воркер/модуль: стройка до конца, прерывание (смерть дозера — прогресс стоит, модуль при LowPower — стоит), завершение активирует здание без roster-перехода и без смены архетипа.
3. Свои юниты выталкиваются из футпринта детерминированно (два прогона — идентичные позиции).
4. LowPower: защита не стреляет, очередь ровно ½ скорости (N тиков → ровно N/2 прогресса за базис 1000), радарные здания теряют радиус обзора (§2.4); GLA не подвержен.
5. Zero-GC на сценарии «стройка + энергосеть» 2000 тиков; инварианты архитектуры.

## 3. Очереди производства и технологическое древо (Production Queues & Tech Tree)

### 3.1 Разделение понятий: `UnitKind` и `BlueprintId`

Два независимых идентификатора, оба protocol-significant:

| Идентификатор | Ширина | Роль | Динамика |
|---|---|---|---|
| `UnitKind` | `u8` | **Класс представления**: как рисовать (меш-класс, радиус кольца). Текущие `Unknown/Scout/Tank/BaseStructure` (`Identifiers.cs:101-116`) расширяются append-only до ~24 классов: `Dozer, Harvester, Infantry, ATInfantry, ScoutVehicle, LightVehicle, MBT, HeavyTank, Artillery, MLRS, AA, Helicopter, Jet, Bomber, TransportAir, CommandCenter, PowerPlant, ProductionBuilding, TechBuilding, Defense, Superweapon, Hero, Drone, Structure` | append-only; перенумерация запрещена (пере-скинит записанных стримов) |
| `BlueprintId` | `u16` | **Точный чертёж**: фракция + имя + все числовые поля (стоимость, время, CombatStats v2, футпринт, энергия, техтребования). Реестр ~170 чертежей 1.0 | append-only; новый реестр Phase 5 |

`BlueprintId` реплицируется в ADD-записи v3 (§6.1) по прецеденту OD-29; `UnitKind` остаётся первым ключом `UnitCatalog` (класс-фолбэк для неизвестных чертежей).

### 3.2 Кольцевая очередь на здание: 5 заказов, 0 B GC.Alloc

```
ProductionQueue (per building, преаллоцировано при спавне здания):
  entries[5] : { BlueprintId u16; TotalTicks u16; RemainingTicks u16; }
  head, count : int        // кольцевой буфер
  WorkMilliAccumulator : int  // базис 1000, для LowPower-замедления
```

- `Produce`-команда (opcode 7): `[building EntityId][blueprintId u16]`. Валидация сервера (фиксированный порядок отказов): `UnknownEntity → NotEntityOwner → EntityNotAlive → TechNotUnlocked → QueueFull → InsufficientFunds`. Списание стоимости — в тик приёма; `RemainingTicks = TotalTicks` из архетипа.
- Продвижение в фазе `AdvanceProduction` тика: если головной заказ есть и здание живо: `WorkMilliAccumulator += LowPower ? 500 : 1000`; каждый накопленный 1000 → `RemainingTicks--`, аккумулятор −= 1000. `RemainingTicks == 0` → спавн.
- **Спавн — через существующий единый chokepoint** роста (`SimulationConstants.MaxUnitsPerMatch`, снапшот-буферы презентации калибруются от него): если ростер полон, заказ **ждёт** (RemainingTicks держится на 0, спавн повторяется каждый тик до места) — не теряется и не рвёт очередь.
- Точка спавна: `origin + ExitOffsetCells` из архетипа (фиксированный выход). Если выход занят своим юнитом — детерминированный сдвиг по канонической спирали до первой свободной позиции.
- Порядок обработки зданий: канонический по `EntityId` (детерминизм).

### 3.3 Точки сбора (Rally Points)

- На здание: `RallyPoint WorldPointMm + HasRally bool` (по умолчанию: `HasRally=false` → свежий юнит стоит у выхода).
- Новый opcode `SetRally = 9` (расширение `GameCommandType` после `UseAbility=8`; `CommandHeader.Validate` расширяет верхнюю границу с 8 до 9 — существующие тесты со значениями ≤8 остаются зелёными).
- Спавн завершается **авторитетным приказом движения**: сервер внутренне формирует Move к rally для новой сущности (тот же путь, что у клиентских команд, но без sequence; документируется как внутренний источник команд — не вход в `CommandHeader.Validate` для клиентов).
- Для зданий-казарм rally по умолчанию задаёт выход + 1 клетка (стандартное поведение RTS; константа архетипа).

### 3.4 Отмена и возврат 100%

- `CancelProduction` — не отдельный opcode: вариант payload команды `Produce` с флагом `Cancel` (экономия опкодов; формат: `[building][blueprintId][slotIndex u8]`).
- Отмена любого слота (не только головного): `Credits = saturatingAdd(Credits, Cost)` — **возврат 100%** по ТЗ; кольцевой буфер уплотняется, головы ниже подтягиваются (детерминированный сдвиг, без аллокаций).
- Отмена завершённого заказа невозможна (слот уже свободен) → `InvalidPayload`.
- Отмена сайта стройки (§2.3) — тот же принцип, 100%.

### 3.5 Технологическое древо: битовые маски

- `TechId` — глобальный реестр до 64 технологий (по ~10-12 на фракцию + общие). Маска `TechMask : ulong` на игрока (§1.1).
- Архетип несёт `RequiredTechMask : ulong` и `RequiredBuildingKinds : ulong`. Доступность: `(player.TechMask & req.TechMask) == req.TechMask && (player.BuildingKindsMask & req.BuildingKinds) == req.BuildingKinds` — чистые битовые операции, ноль аллокаций.
- Технология выдаётся событийно: постройкой здания-исследователя (например, Propaganda Center открывает технологии China) или исследованием (заказ в здании как элемент очереди производства с `blueprintId` технологии; по завершении — бит в `TechMask`, приватная синхронизация владельцу §1.5).
- Клиент UI: дерево рисует из того же реестра чертежей (единый источник данных для сервера и клиента; клиентский реестр — зеркальная копия, версионируется вместе с `BlueprintId`).

### 3.6 Тесты раздела (DoD-фрагмент)

1. Кольцевая очередь: 5 заказов, переполнение → `QueueFull`; отмена из середины — корректное уплотнение; 0 B GC.Alloc на 1000 тиков с полными очередями (профилировщик + инварианты).
2. LowPower: ровно ½ скорости (2000 тиков LowPower = 1000 «полных» тиков прогресса).
3. Rally: свежий юнит получает движение к точке в тик спавна; смена rally не перезадаёт движение уже созданным юнитам.
4. Спавн при полном ростере: заказ ждёт, не теряется; после снятия лимита спавнится.
5. Техдерево: недоступность по маске и по зданию; разблокировка исследованием и постройкой.
6. Детерминизм: бит-равные чексуммы двух прогонов сценария «казарма+фабрика, 20 заказов, 2 отмены, LowPower эпизод».

## 4. Матрица типов брони и урона (Damage & Armor Matrix)

### 4.1 Классификации

**ArmorType (7):** `Infantry, HeavyInfantry, LightVehicle, HeavyVehicle, Aircraft, Structure, Fortified`.
**DamageType (8):** `SmallArms, HeavyMachineGun, AntiTankCannon, GuidedMissile, ArtilleryExplosive, ThermobaricNapalm, ToxinChemical, HighTechLaser`.

Соответствие формулы Generals: Infantry/HeavyInfantry — лёгкая/тяжёлая (бронежилеты, киборги) пехота; LightVehicle — багги/хамви/лёгкие БТР; HeavyVehicle — ОБТ и сверхтяжи; Structure — обычные здания; Fortified — бункеры/бетон (для них артиллерия нужна, стрелковое бесполезно).

### 4.2 Матрица множителей, базис 1000 = 1.00×

Строки — тип урона, столбцы — тип брони. `M[damage][armor]`:

| Урон ↓ \ Броня → | Infantry | HeavyInfantry | LightVehicle | HeavyVehicle | Aircraft | Structure | Fortified |
|---|---|---|---|---|---|---|---|
| **SmallArms** | 1000 | 700 | 500 | 250 | 500 | 300 | 100 |
| **HeavyMachineGun** | 700 | 1000 | 800 | 300 | 700 | 400 | 100 |
| **AntiTankCannon** | 400 | 600 | 1000 | 1000 | 200 | 800 | 600 |
| **GuidedMissile** | 500 | 500 | 1000 | 900 | 1000 | 600 | 300 |
| **ArtilleryExplosive** | 1500 | 1200 | 800 | 700 | 0 | 1200 | 1000 |
| **ThermobaricNapalm** | 1500 | 1400 | 600 | 400 | 0 | 800 | 200 |
| **ToxinChemical** | 2500 | 1800 | 400 | 150 | 0 | 300 | 150 |
| **HighTechLaser** | 1000 | 1000 | 800 | 700 | 1000 | 600 | 400 |

Свойства (проект, Owner Decision для чисел):

- Легаси-пара **(SmallArms → Infantry) = 1000**: конструктор `CombatStats` без явных типов отображается на эту пару → существующие 1392 теста продолжают давать бит-в-бит те же уроны (см. 4.4).
- Стрелковое бесполезно против брони/фортификаций (250/100); АТ-пушка — король брони, но слаба по воздуху (200) и пехоте (400); ракеты — точный универсал с монополией на адекватный ответ авиации (1000) и лёгкой технике (1000); артиллерия и напалм — анти-пехота/анти-здания, бессильны по авиации (**0** — самолёт выше зоны поражения); лазер — дорогой точный универсал без нулевых клеток (фракционная фишка USA, §5.1).
- Диапазон значений [0…2500]: переполнение исключено даже в `long`-умножении (см. 4.3).

### 4.3 Целочисленная формула урона

```
applied = (int)( (long)BaseDamage * Matrix[damageType][armorType] / 1000 )
```

- Умножение в `long` (макс. 1000×2500 = 2 500 000 — вне опасности), деление целочисленное **с усечением вниз** — платформо-независимо и детерминированно.
- Формула исполняется в `CombatTickResolver` на этапе `CommitShot` (значение в `DamageEvent` сразу финальное — в событии едёт применённый урон, клиентская презентация не пересчитывает матрицу).
- Площадный урон (артиллерия/ТОС/напалм): сплэш-резолвер в тик выстрела собирает цели в радиусе `SplashRadiusMm` от точки падения **в каноническом порядке `EntityId`** и применяет ту же формулу с затуханием `FallOffPerMm` (целое, basis 1000 на метр). Поиск целей — линейный скан по canonical-массиву (O(N) на выстрел, N ≤ 1024 — приемлемо для Phase 5; пространственный индекс выстрелов — оптимизация Phase 8). Порядок фиксирован → детерминизм.
- Горение (напалм): `BurnTicks` + `BurnDamagePerTick` в архетипе — DoT-накопитель в записи юнита, тикает в фазе экономики, целые значения.

### 4.4 CombatStats v2 — обратная совместимость без единого сломанного теста

```
CombatStats (v2):
  MaximumHealth, Damage, RangeMm, CooldownTicks      // без изменений
  ArmorType  : byte = ArmorType.Infantry             // новые поля со значениями по умолчанию
  DamageType : byte = DamageType.SmallArms
```

- Существующий конструктор `CombatStats(health, damage, range, cooldown)` (`CombatSimulation.cs:12`) сохраняет сигнатуру и семантику: поля типов получают `(SmallArms, Infantry)`, матричная клетка = 1000 → **урон бит-в-бит совпадает** с текущим поведением; 1370 EditMode-тестов, проверяющих величины урона, не меняются.
- Новый конструктор с явными типами — для архетипов Phase 5; валидация расширяется (`ArmorType < 7`, `DamageType < 7`).
- `MatchConfig.UnitStats` остаётся как есть (легаси-матчи); новые матчи собираются из реестра архетипов (§5.7).

### 4.5 Тесты раздела (DoD-фрагмент)

1. Бит-в-бит регресс: полный прогон существующего боевого сценария до/после v2 — идентичные `StateChecksum`.
2. Матрица: полнота (7×7), диапазон [0…2500], легаси-клетка ровно 1000; индексация по enum.
3. Формула: усечение вниз (99×999/1000 = 98), отсутствие переполнений на граничных значениях.
4. Сплэш: канонический порядок целей; затухание; авиация не поражается залпом по земле.

> **Статус раздела:** R&D-проект базового ростера 1.0. `GDD.md:29` держит конкретные ростеры как `TBD / Owner Decision Required`; настоящий ТЗ прямо требует полный перечень — поэтому ниже дан исчерпывающий проект для утверждения владельцем. ### 5.1 USA — технологическое превосходство

**Доктрина.** Дорогие, но точные и автономные силы: дроны, лазеры, лучшая авиация, экономика на сбросах припасов. Сильны в разведке и точечных ударах; уязвимы ценой и массой дешёвых юнитов противника. Игровой характер: «качество против количества», поздняя мощь.

**Уникальные механики (реализация):**
1. **Боевые дроны** — на выбранной технике строится дрон-охранник (маленькая сущность, `UnitKind=Drone`, автозахват в радиусе носителя): спавн-подсущность через стандартный chokepoint; дрон висит над носителем (позиция = позиция носителя, отдельная `EntityId`).
2. **Лазерное оружие** (`HighTechLaser`): мгновенное попадание (без снаряда — урон в тик выстрела), в матрице нет нулевых клеток; эксклюзив USA.

### 5.3 GLA — партизанская асимметрия

**Доктрина.** Нищая, хитрая, тотально мобильная армия без энергосети: туннели, металлолом, стелс, дешёвые ловушки. Компенсирует слабую технику асимметричными ударами. Игровой характер: «тень войны».

**Уникальные механики (реализация):**
1. **Salvage (сбор металлолома)** — уничтоженная техника оставляет `SalvageCrate` (сущность-лут, 3-$-эквивалент апгрейда): подобравший техник получает перманентный апгрейд ствола (целочисленный множитель basis 1000, максимум 3 уровня на сущность).
2. **Tunnel Network** — входы-туннели: юнит входит в один вход, через `TunnelTravelTicks` (50) появляется у выбранного входа той же сети (все входы игрока образуют сеть). Очередь телепорта — детерминированная, по (времени входа, `EntityId`); вместимость туннеля 10 юнитов. Юниты в туннеле не входят в боевой ростер (не могут быть целью и не считаются «живыми» для исхода боя §7.4); при уничтожении последнего входа сети все юниты в туннелях уничтожаются.
3. **0 потребности в энергии** — все `PowerDelta = 0`; `LowPower` для GLA всегда false (§2.4).
4. **Стелс** — отдельные юниты/здания невидимы вне радиуса `RevealStealthRadiusMm` детекторов (расширение движка §6.6: стелс-бит в снапшоте видимости, детекторы открывают).

### 5.5 NATO — единое тактическое поле

**Доктрина.** Коалиционная сетецентричная армия: превосходство разведки и целеуказания, загоризонтные удары, гибкие универсальные платформы. Сильны информацией и артиллерией; уязвимы в прямом танковом обмене. Игровой характер: «вижу всё — бью издалека».

**Уникальные механики (реализация):**
1. **Единое тактическое поле (Unified Tactical Field)** — юниты NATO автоматически видят всё, что видят союзные юниты в радиусе `TacticalFieldRadiusMm` (проект 30 000 мм) от них: реализация — расширение движка видимости (§6.6): friendly-соседство NATO-юнита расширяет его собственную маску чужими разведданными в радиусе поля. Детерминированно, пер-тик, Zero-GC.
2. **Загоризонтная наводка (Over-the-Horizon Targeting)** — артиллерия NATO может обстреливать цели, видимые **союзником** (в 2v2 — напарником), вне собственной прямой видимости: серверный автозахват и приказ Attack принимают цель из team-видимости для юнитов с флагом `CanUseSharedTargets` (маска видимости команды уже существует — §7.2).
3. **Модульное строительство** (как Russia, §2.3).

## 6. Сетевой протокол и Anti-Cheat тумана войны

> Изменения провода — protocol-significant: по `DEVELOPMENT_STANDARD.md` (Architecture Rules) каждое требует compatibility review и ADR. Настоящий R&D — вход в этот ADR. Прецедент расширения уже есть: OD-29 добавил `UnitKind u8` к ADD-записи (v1→v2, hard break), сохранив зелёный набор тестов.

### 6.1 Дельта-протокол v3 и командный кодек v2 (аддитивно, по прецеденту OD-29)

**Дельта-протокол v3** (`DeltaSnapshotProtocol.Version = 3`):

1. **ADD-запись: 42 B** = 40 B v2-записи + `BlueprintId u16` (little-endian) в хвосте. Тот же принцип, что у OD-29: v2-префикс остаётся байт-в-байт записью v2-пира, новый идентификатор — в конце. Keyframe-слайсы и дельты производятся одним писателем (факт RND Rev2 / док `DeltaAddRecord`), поэтому расширение автоматически покрывает оба потока; `KeyframeStaging` пересчитывается из `AddRecordSizeBytes` (4096 × 42 = **172 032 B** на клиента вместо 163 840 B; `ServerReplicationEmitter.cs:317-319`).
2. **UPDATE-запись: расширенная маска.** Бит 7 `UnitDirtyMask` (`ReservedExtension`, отвергается в v2 — `DeltaSnapshotProtocol.cs:165`) в v3 переименован в `HasExtendedMask`: за первым байтом маски следует второй байт `UnitDirtyMaskV3` с битами `BuildProgress = 1<<0` (u16, basis 1000) и `AuxState = 1<<1` (u16, семантика по архетипу: остаток склада в $ для `SupplyDock`, флаги оккупации и т.п.). Максимальный UPDATE v3 = 44 + 1 + 2 + 2 = **49 B**. v2-пир получит пакет с битом 7 и отвергнет его — hard break v2↔v3, ровно как v1↔v2 (зеркальная логика `Version = 2` док-комментария).
3. **REMOVE-запись: без изменений.** Причины `Destroyed=0, FogOfWarHidden=1` (`DeltaSnapshotModel.cs:14-27`) достаточны: «призраки» §6.3 — клиентская презентация, а не протокольное состояние.
4. **Заголовок: без изменений** (36 B); `MaxPayloadBytes = 8192` и multipart-механика `PartIndex/PartCount` сохраняются.

**Командный wire-кодек v2** (`CommandWireCodec.Version = 2`): расширяет `TryDecode` (`CommandWireCodec.cs:143-147` сейчас принимает только Move/Attack/Stop) тремя новыми типами; раскладка существующих Move/Attack/Stop не меняется. Форматы — Приложение А. `GameCommandType` получает `SetRally = 9` (после `UseAbility = 8`); верхняя граница валидации `CommandHeader.Validate` поднимается с 8 до 9 — все существующие тесты со значениями ≤ 8 остаются зелёными.

**Транспорт:** новый `TransportMessageType.PlayerStateSync = 15` — следующий свободный после `ClientReadyToResume = 14` (12/13 заняты standalone reconnect-опкодами, `TransportProtocol.cs:26-51`); канал C0 (reliable), строго per-session (§1.5).

### 6.2 Новые реплицируемые поля сущности

`ServerUnitSnapshot` / `DeltaAddRecord` расширяются зеркально прецеденту `UnitKind` (`MatchServer.cs:97-101`):

| Поле | Тип | Где ездит | В `StateChecksum` |
|---|---|---|---|
| `BlueprintId` | u16 | ADD и keyframe (идентичность, immutable) | **нет** — как `UnitKind`: идентичность, не состояние |
| `BuildProgressMilli` | u16 | UPDATE (бит `BuildProgress`) | **да** — детерминированное игровое состояние, как Health |
| `AuxState` | u16 | UPDATE (бит `AuxState`) | **да** |
| `Owner` | существующий бит | захват Oil Derrick меняет владельца — уже реплицируется | да (как сейчас) |

Правило детерминизма: `BuildProgress`/`AuxState` — целые, меняются только фазами тика; их попадание в per-client `StateChecksum` (OD-40) автоматически расширяет desync-диагностику на стройку и экономику видимого мира.

### 6.3 Туман разведанного (Explored Fog / Ruins): призрак последнего известного состояния

Требование: при уходе здания в туман клиент сохраняет «призрак» последнего известного состояния. Решение — **клиентский ghost-слой**, без новых протокольных сущностей:

1. Сервер при потере видимости шлёт REMOVE с причиной `FogOfWarHidden` — как сейчас для юнитов.
2. `ClientReplicationWorld` (не презентация — мир) для **структурных архетипов** (`UnitKind` класса здания: `CommandCenter`, `ProductionBuilding`, `Defense`, `Superweapon` и т.п.) перед удалением слота переносит последнюю известную запись `{BlueprintId, позиция, Owner, Health, BuildProgress}` в **ghost-реестр**: преаллоцированный массив `GhostRecord[1024]`, ключ — битовый индекс `EntityId` (тот же диапазон, что `BitMask1024`), 0 B GC.Alloc.
3. Юниты (не здания) призраков не оставляют — исчезают, как сейчас (формула Generals: техника не «помнится» картой).
4. Обновление призрака: сущность снова видна → обычный ADD/UPDATE освежает слот, ghost-запись гасится. Сущность уничтожена, пока была видна → REMOVE `Destroyed` гасит и слот, и ghost.
5. Сущность уничтожена, пока была в тумане → сервер REMOVE не генерирует (её не было в видимом срезе клиента) → **призрак живёт до повторной разведки** — целевое поведение «Ruins»: игрок видит устаревшее здание, пока не проверит.
6. Ghost-слой **не входит** в `StateChecksum` и в `FogOfWarRemoveCount`: это производная презентационная память от легально полученных данных, а не реплицированное состояние. Анти-оракул: в ghost не попадает ничего, чего клиент не видел своими глазами (своей/союзной маской) — сервер ничего не добавляет.

### 6.4 Полная изоляция строек в неразведанных зонах (анти-мапхак)

Три контура, все уже существуют или тривиально выводятся из существующих:

1. **Поток:** каркас — сущность; `FogOfWarReplicationFilter` не пускает невидимые сущности в per-client срез. Вражеская стройка в неразведанной зоне не порождает ни ADD, ни UPDATE, ни REMOVE — бит-уровневая проверка тестом (§6.8).
2. **Команды:** `Build` валидируется по **собственной** карте разведки игрока `ExploredCells` (§2.2) — отказ `NotExplored` не раскрывает геометрию карты (в отличие от проверки коллизий, которая «подсветила» бы занятость). Проверки коллизий выполняются только после прохождения `NotExplored`.
3. **Чексумма:** per-client `StateChecksum` (OD-40) считается по отфильтрованному срезу — клиент A и клиент B имеют разные чексуммы по построению; скрытая стройка не влияет на чексумму наблюдающего.

### 6.5 Приватный экономический канал

`Credits`, `TechMask`, очереди — только владельцу через `PlayerStateSync` (§1.5): надёжный C0, latest-wins, идемпотентный. Союзники приватных данных друг друга не получают. Прямая криптографическая сверка приватного слоя не предусмотрена (§9, открытый вопрос); целостность обеспечивается детерминизмом сервера и реактивными отказами `InsufficientFunds`.

### 6.6 Расширение движка видимости (пер-юнитный радиус, стелс, тактическое поле)

`VisibilityEngine` получает **аддитивную перегрузку** — легаси-сигнатура остаётся и делегирует с радиусом по умолчанию (ни один существующий тест не меняется):

```
CalculateVisibility(units, unitCount, playerVisibilityOut, ReadOnlySpan<int> sightRadiusPerUnit)
```

- **Радиус из архетипа:** здания (проект 15 000–25 000 мм), разведчики (25 000+), обычные юниты (20 000 = текущий `DefaultSightRadiusMm`). Побочная выгода: `FogOfWarReplicationFilter` больше не обязан знать глобальный радиус — радиус приходит со снапшотом каждой сущности.
- **Стелс (GLA):** бит `IsStealth` в архетипе. Правило: стелс-сущность невидима врагу, пока не находится в радиусе `RevealStealthRadiusMm` (проект 12 000) любого friendly-юнита-детектора противника (детекторы — тоже флаг архетипа: Pathfinders, Sensor Array, радары). Реализация: пасс после основного расчёта — очистка битов стелс-сущностей, не покрытых детекторами; детерминированный линейный скан, Zero-GC.
- **Тактическое поле NATO:** юниты с флагом `TacticalField` заимствуют видимость союзных сущностей в радиусе `TacticalFieldRadiusMm` (проект 30 000): пасс OR масок — `mask |= union союзных масок в радиусе` (маски уже вычислены к этому моменту — порядок пассов фиксирован: расчёт → стелс → тактическое поле). В 2v2 это естественно расширяется на союзника (§7.2).
- **Радар при LowPower:** радарные здания получают радиус 0 (§2.4) — просто значение из архетипа, обнулённое флагом питания; движку изменений не нужно.

### 6.7 Пропускная способность и бюджеты

| Поток | Оценка | Бюджет |
|---|---|---|
| ADD v3 (42 B) при полном keyframe на 400 сущностей | 16 800 B | keyframe-слайс ≤ 16 384 B → 2 слайса; существующая механика |
| Стройка: 10 зданий × UPDATE ~7 B (id+маска+ext+u16) | ~70 B/тик во время строительства | pacing 2048 B/тик — <4 % |
| Экономика видимого мира: `AuxState` складов | единицы B/тик при изменениях | пренебрежимо |
| Приватный `PlayerStateSync` | ≤ 128 B × 10 Гц | 1.3 KB/s на игрока (C0, вне C2-pacing) |
| 4 клиента (2v2) | 4 × per-client слайсы | pacing индивидуален на клиента; эмиттер уже per-client (`LastAckedTick`, OD-12) |

Вывод: v3 не меняет пропускную картину Phase 4 (узкое место — движущиеся юниты, 54–98 % потолка при 400 юнитах, RND Rev2); стройка и экономика добавляют проценты, не порядки.

### 6.8 Тесты раздела (DoD-фрагмент)

1. Кодеки: round-trip ADD 42 B / UPDATE 49 B / три новые команды; v2-пир отвергает v3-пакет (бит 7) и наоборот; v2-команды Move/Attack/Stop байт-в-байт совместимы с v1-раскладкой.
2. Ghost: здание ушло в туман → ghost-запись; повторная разведка → свежий слот; уничтожение в тумане → ghost жив; `StateChecksum` не содержит ghost-данных; 0 B GC.Alloc на 1000 операций.
3. Изоляция: клиент A не получает ни байта о стройке B в неразведанной зоне (бит-сравнение потоков с/без скрытой стройки); `Build` в неразведанное → `NotExplored` без утечки занятости.
4. Видимость: пер-юнитный радиус (здание-разведчик), стелс + детекторы, тактическое поле NATO (заимствование союзной маски в радиусе), радар = 0 при LowPower.
5. Захват Oil Derrick: смена `Owner` реплицируется существующим битом;AuxState склада виден только при разведке.

## 7. Топология 2v2 (Milestone M2, OD-48)

### 7.1 Конфигурация слотов и runtime-композиция

Слоты и команды уже определены в Core (`MatchTopology2v2.cs:13-22`): Red = игроки 1–2 (слоты 0–1), Blue = игроки 3–4 (слоты 2–3). M2 — это **композиция, а не новый протокол**:

1. `DedicatedServerRunner.RequiredPlayersForStart`: 2 → **4** (константа M1-скоупа, `DedicatedServerRunner.cs:39-44`; изменение сопровождается отдельной веткой конфигурации `MatchTopology = OneVsOne | TwoVsTwo`, чтобы 1v1-серверы остались доступными).
2. **Подключение боевого отношения:** `ServerHost` получает перегрузку/фабрику, создающую `MatchServer(new Team2v2CombatRelation(), filter)` вместо дефолтного `SkirmishCombatRelation` (`ServerHost.cs:124-135`, `MatchServer.cs:193-205`; шов существует, backlog `[OPEN — M2]` в `CURRENT_STATE.md:112` — закрывается этим шагом).
3. **Подключение команд в видимость:** при старте матча сервер вызывает `FogOfWarReplicationFilter.SetPlayerTeam` для всех четырёх игроков (метод уже существует, `FogOfWarReplicationFilter.cs:79`), а `VisibilityEngine.SetPlayerTeam` заполняет `_teamByPlayer`.
4. **Командная геометрия спавна** — фикс расхождения `BuildDefaultMatchConfig` (`DedicatedServerRunner.cs:366`), которая сейчас кладёт стороны по чётности индекса (второй игрок Red попадал бы в зону Blue). Новая геометрия: команда по `MatchTopology2v2.GetTeamForSlot`, позиция базы — функция (команда, слот в команде): Red при X < 0, Blue при X > 0, союзники разнесены по Z на 60 000 мм, между командами 120 000+ мм. Зеркальная симметрия на 180° — сопоставимые стартовые условия (требование GDD к картам).

### 7.2 Shared Vision: побитовое объединение масок

Требование ТЗ: `OwnMask | AllyMask`. Ключевой факт кодовой базы: **движок уже вычисляет именно это объединение**. Правила `VisibilityEngine` (`VisibilityEngine.cs:35-40`):

- правило 2 — юниты игроков одного `TeamId` всегда видимы (союзник виден сам по себе);
- правило 3 — враг видим в радиусе обзора **любого friendly-юнита** (своего или союзного: `_friendlyOwner` строится из командной карты, `BuildFriendlyOwnerLookup`).

То есть выходная маска игрока A уже является объединением: всё, что видят A и его союзник как sight-источники, плюс все союзные сущности. «Подключить Shared Vision» = выполнить п. 3 §7.1; ни одного изменения в расчёте масок не требуется.

Свойства изоляции (анти-мапхак сохраняется):

- Маски **не покидают сервер**: клиенту уходит только его отфильтрованный срез (per-client change-set, OD-12/OD-40). Клиент не может отличить «увидел сам» от «увидел союзник» — и не должен.
- Союзник не получает приватные данные (§1.5): экономика и очереди остаются per-player.
- Чексумма: per-client, по своему срезу — Shared Vision расширяет срез, но не выравнивает чексуммы разных клиентов.

Загоризонтная наводка NATO (§5.5) опирается на ту же командную маску: цель легальна для артиллерии NATO, если она в маске **команды** стреляющего (у закрыть: цель в маске союзника, но не в своей — серверная проверка по team-маске, детерминированная).

### 7.3 Запрет дружественного огня

Три контура (два готовы, один добавляется):

1. **Автозахват и бой:** `Team2v2CombatRelation.AreEnemies` (`CombatRelation.cs:113`) — союзники не враги: не выбираются целями автозахвата, урон не применяется.
2. **Явные приказы:** `MatchCommandRejection.FriendlyTarget = 11` (уже в коде, `MatchServer.cs:39-44`) — Attack на союзника отклоняется на пути команды.
3. **Площадный урон (новое):** сплэш-резолвер (§4.3) фильтрует цели по `AreEnemies(shooter, target)` — снаряды ТОС/артиллерии не ранят союзников. **Отклонение от формулы Generals** (там сплэш бьёт всех): введено требованием ТЗ («запрет дружественного огня между союзниками»); помечено как Owner Decision — при желании вернуться к Generals-поведению меняется один фильтр в сплэш-резолвере.

### 7.4 Командное условие победы

- `Team2v2CombatRelation.DetermineOutcome` (`CombatRelation.cs:116`) уже возвращает `BattleOutcome.TeamVictory(team)`, когда живые combatants принадлежат одной команде; `ServerHost.OnDriverTickDue` (`ServerHost.cs:799-834`) уже разносит терминацию `MatchFinished` по сессиям. Победа команды = уничтожение всех сущностей противников (юниты и здания — здания являются combatants со своими `CombatStats`).
- GLA-туннели: юниты в туннелях вне боевого ростера; команда, у которой остались только юниты в туннелях (и не осталось входов), считается уничтоженной — правило §5.3 (содержимое погибает с последним входом).
- **Дисконнект в 2v2:** текущее поведение сохраняется (grace-окно 4000 тиков / 200 с, OD-18; сущности остаются во владении отключившегося). Передача контроля союзнику — **TBD / Owner Decision Required** (не входит в M2-скоуп; фиксируется в §9).
- Ничья: обоюдное уничтожение последних сущностей в одном тике → `BattleOutcome.Draw` (существует).

### 7.5 Клиентская презентация команд

- Минимальные изменения клиента (без Phase 7-полиша): `MinimapRadarModel` выводит третий класс принадлежности «ally» (сейчас local/enemy/neutral — расширение классификации, презентационное); цветовые схемы команд; HUD статуса союзника (только публичные данные: его видимые сущности, сам факт подключения).
- Выбор союзных юнитов: разрешён для **просмотра** (в срезе они есть), приказы чужим юнитам отклоняются сервером (`NotEntityOwner` — уже в коде).

### 7.6 Тесты M2 (DoD-фрагмент)

1. Композиция: `DedicatedServerRunner` с `TwoVsTwo` стартует матч при 4 игроках; команды по `MatchTopology2v2`; геометрия спавна зеркальна (расстояния сопоставимы с точностью до симметрии).
2. Shared Vision: юнит союзника открывает врага в радиусе своего обзора → враг появляется в срезе игрока A (маска A содержит цель, которую видит только B); без командной карты — не появляется (контроль).
3. Friendly fire: автозахват не выбирает союзника; Attack-приказ → `FriendlyTarget`; сплэш ТОС не ранит союзника в эпицентре.
4. Team victory: уничтожение всех сущностей одной команды → `TeamVictory` → все 4 клиента получают `MatchFinished`; выживший игрок побеждённой команды не продлевает матч.
5. 4-лег live UDP: существующий `Match2v2PlaytestScenarioTests` (4 виртуальных лега, бит-равенство чексумм, реконнект-сценарий) переводится из «задела» в приёмку M2 + добавляется live-UDP вариант по образцу M1.2 (снятие оговорки OD-48 «четыре сокета не доказывают 2v2» — теперь доказывают: командная композиция + Shared Vision + team victory проверены явно).
6. Реконнект одного члена команды среди боя: grace-пауза, возобновление, слайсы обоих союзников консистентны.
