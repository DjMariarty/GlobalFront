## 2. Закрытие замечаний

### F-1 / N-1 — утечка оверрайда здоровья: **ЗАКРЫТО**
Ветка исчезновения (`!world.TryGetSlotState`) при `_slotNewestTick[slot] != EmptyTick` → `ClearSlot(slot)` **плюс** явный
`_slotInvMaxHealth[slot] = 0f` и `_slotHealthOverridden[slot] = false` (`UnitViewTickBuffer.cs:468–484`).
Ветка рецикла переведена на идентичность: `var tookOverUnit = _slotEntity[slot] != 0;` (`:504`) — и это **корректный свидетель**:
`EntityId.IsValid => Value != 0` (`Identifiers.cs:15`), то есть 0 зарезервирован под «нет сущности».
Дополнительно введён отдельный флаг `_slotHealthOverridden` (`:286`), который различает «денаменатор не назван» и «назван 0»
(явный ноль = пустая полоса) — без этого различия `!hadSample && _slotInvMaxHealth == 0` было неотличимо от «не разрешено».

**Оценка архитектурного решения не чистить оверрайды в `Flush()` — ПРИНЯТА и обоснована.**
`ClearAllSamples()` намеренно сохраняет `_slotEntity` и денаменатор («Slot identity and resolved maximum health survive»,
`:1153–1160`), потому что `Flush()` обслуживает OD-18-паузу, где юниты те же; очистка там обнулила бы полосу навсегда для
pre-OD-29-записей, у которых денаменатор знает только биндер. Смена юнита через Flush/Resync при этом **гарантированно** снимает
старый оверрайд именно за счёт идентичности: `recycled == true && tookOverUnit == true` — свидетель не зависит от истории,
которую `ClearAllSamples` стирает. ProbeA-контрпример в этом сценарии не воспроизводится; оба F-1-теста падают на откатанном
свидетеле и зелёные на текущем коде (пп. 3–4 метода).

Три заявленных теста проверены по коду и на прогоне:
`SetSlotMaximumHealth_DeathFollowedByNewUnit_ResolvesFromCatalog` (50/123 → 50/200 = 0.25),
`SetSlotMaximumHealth_ResyncHandover_ResolvesFromCatalog` (handover без пустого пакета, через `Resync`),
`SetSlotMaximumHealth_SurvivesFlushOfTheSameUnit` (пауза сохраняет 50/123 — защита принятого решения от «улучшения»). ✅

### F-2 — связка констант дрейфа: **ЗАКРЫТО**
`private const double DriftSnapTicks = MaxRenderDelayTicks + MaxExtrapolationTicks + 2.0;` (`:238`) = **16.0**, подтверждено
reflection (ProbeB: `DriftSnapTicks=16, maxLegitSkew=14`). Константа выведена из границ, определяющих легитимную величину
рассогласования (максимум = `MaxRenderDelayTicks` + `MaxExtrapolationTicks` = 14), а не из `HistoryTicks * 0.5`; запас +2.0 —
именно то, что не даёт `Advance` счесть запаркованные часы перелётом. Комментарий фиксирует инвариант и называет пограничный
тест `Starvation_HighDelay_DoesNotSnapClockBackwards`, который обязан быть перепроверен при смене любой из трёх констант.
Дополнительно снэп стал **односторонним** (`if (skew < -DriftSnapTicks)`, `:649`) — обратный снэп звездившихся часов физически
невозможен. ProbeD: реальное отставание 22 тика снэпится вперёд ровно в `capturedTick - delay` (98.96 → 118 = 130 − 12),
60 кадров голодания строго монотонны и парковка встаёт на `capturedTick + MaxExtrapolationTicks` (132), из них 47 кадров
шли вперёд. ✅

### F-4 — outlier-кламп в `ObserveArrival()`: **ЗАКРЫТО**
`private const double MaxIntervalSampleTicks = 8.0;` (`:246`) — 5 Гц-пол (4 тика) + один потерянный пакет; кламп стоит **один раз
перед обеими ветками** (`:1067–1070`, до ветки первичной оценки `_observedIntervalTicks <= 0` и до EMA), поэтому обрезается и
холодный первый интервал, и последующие. Тест `ObserveArrival_LargeGap_DoesNotSpikeDelayToCeiling`: после устоявшихся 10 Гц
дыра в 31 тик (`ReprimeCount == 0`, ниже гейта) даёт `RenderDelayTicks <= 8` и через три номинальных пакета `< 6`,
`ObservedIntervalTicks < 2.7`. ProbeE: холодный первый интервал = ровно 8 (обрезан, а не сырые 30). ✅

### Zero-GC контракт: **ПОДТВЕРЖДЁН**
- Штатный `ZeroGC_SustainedOperation` (CaptureTick + Advance + TrySample ×64 слота, 1000 итераций) — 0 байт, с **негативным
  контролем** (`new byte[4096]` обязан быть пойман рекордером) — методологически корректно: молчание рекордера доказано значимым.
- **ProbeC** расширяет измеряемое окно на ветки, которых штатный тест не касается: юнит с attack target (мировой lookup турели
  через `world.TryGet`), смерть (ClearSlot + сброс оверрайда) и рецикл (`tookOverUnit`-сброс) — **0 байт**, при этом
  `RecycledSlotCount` в окне вырос (т.е. ветки реально исполнялись, тест не вырожден).
- По коду: всё состояние — плоские массивы (один массив на поле, `capacity × 32`); `Array.Clear`, копии структур, `in`-параметры,
  `Math.*`, поиск слотов по индексу; каталог — массив по байту kind (`UnitCatalog.cs:66–70`);
  ни LINQ, ни `foreach` по интерфейсам, ни боксинга, ни строк, ни исключений в горячем пути; у самого класса **нет зависимостей
  от UnityEngine**. `UnitViewPose` — `readonly struct`, `new` в `WritePose` не аллоцирует.
- Дисконтинуити-пути (`Flush`/`Resync`/`Reprime`: `Array.Clear` + два линейных цикла) аллокаций не содержат по построению; они не
  входят ни в один измеряемый прогон, что для них и правильно (вызываются на разрыве, не покадрово).

## 3. Остаточные замечания (не блокирующие)

### R-1 (P3 / Info) — оверрайд, названный до первого сэмпла, достаётся следующему юниту
`SetSlotMaximumHealth(slot, max)` не принимает идентичность, поэтому «для кого назван денаменатор» буфер свидетельствует только
через `_slotEntity`. Обе защиты F-1 ключуются на состояние, которого невиденный юнит не создал: death-ветка требует
`_slotNewestTick != EmptyTick`, а свидетель рецикла — `_slotEntity != 0`. Как следствие, слот, у которого оверрайд назван, но
который **ни одного сэмпла не получил**, отдаёт оверрайд следующему юниту.
**Доказательство (ProbeA, FAILED):** `SetSlotMaximumHealth(0, 123)` → в слот приходит Scout (каталог 200) со 50 HP →
`HealthFraction = 0.406504` (= 50/123) вместо каталожных `0.25`.
**Оценка:** это обратная сторона осознанного решения «биндер, назвавший денаменатор до прихода юнита, назвал его для этого
юнита» (`:491–503`); различить «названо заранее для incoming» и «названо для погибшего и ни разу не увиденного» по состоянию
буфера невозможно. На `HEAD` этот угол вёл себя иначе (оверрайд смывался на первом же рецикле) — то есть ремедиация **сдвинула**
неоднозначность, а не породила новый отказ в рабочем пути: **`SetSlotMaximumHealth` сегодня не вызывается ни одним продовым
кодом** (в `Runtime` есть только `_buffer.Resync(...)` из `UnitViewBinder`), а последствие — неверный денаменатор полосы, не NaN
и не краш.
**Рекомендация (backlog):** сделать свидетель точным — `SetSlotMaximumHealth(int slot, ulong entity, int maximumHealth)` (или
геттер «для какой сущности назван оверрайд»), тогда класс неоднозначности исчезает целиком.

### R-2 (Info) — формулировка F-4 верна для «прогретого» оценщика
Кламп ограничивает **сэмпл**, а не саму задержку. Если широкая дыра оказывается *первым* наблюдаемым интервалом (холодный
старт), обрезанные 8 всё равно дают `delay = 2×8 = 16 →` потолок 12, и восстановление занимает 8 номинальных пакетов
(измерено ProbeE: `cold delay=12`, «packets to delay<6 = 8 → 5.80»). Задержка при этом ограничена потолком и самовосстанавливается,
то есть дефекта нет; фразу «стоит меньше одного пакета дополнительной задержки» следует читать как случай устоявшегося оценщика
(ровно тот сценарий, который F-4 и описывает). Рекомендуется уточнить в комментарии.

### R-3 (Info) — `Flush()` не имеет продового вызова
Контракт «оверрайд переживает паузу OD-18» защищён тестом, но сам `Flush()` из `Runtime` никто не вызывает (только `Resync`,
который вызывает его внутри). Пока это означает, что ветка «пауза» проверена только тестами; при подключении OD-18-паузы
стоит помнить, что `Flush()` не сбрасывает `_renderTick` (сброс произойдёт в `Advance` через `_needsRenderClockAnchor`).
