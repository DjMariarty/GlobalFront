Four (D-1, D-3, D-4, D-9) are closed *as scoped* but the invariant each one serves is still violated by a sibling path the remediation campaign never enumerated — and in three of those four cases the sibling path has **no test at all**.

**Headline findings:**

1. **N-01 (P1).** The D-1 anti-hijack guard exists only on the *connect* path. `HandleReconnectRequest` performs no connection-ownership check and `TransportSessionBinder.Bind`/`Release` are not inverses, so one socket can own an arbitrary number of live sessions, orphan bindings permanently, and drive `BoundCount` to `MaxPlayers` — after which the server returns `ServerFull` to every legitimate client **forever**, with no code path that ever decrements the count. 2. **N-02 (P2, new — not in either prior report).** The **production** carrier's C2 receive path allocates `2 + N` objects per fragmented snapshot, because `LiteNetLibCarrier.HandleSnapshotReceive` routes reassembly through the same `FragmentAssembler` the own carrier uses. This contradicts invariant §2.1 ("receive", "keyframe slice reassembly") *and* the carrier's own inline claim that "the only owned allocation this path makes is the message handed to the event queue". No test measures it; the two receive-path allocation tests explicitly **budget** two allocations (`baseline == 2`) instead of asserting zero.

3. **N-03 (P2).** The client's default REMOVE sink (256) is smaller than the server's REMOVE budget (512), so a legal cumulative catch-up delta is discarded and mislabelled as *malformed*. The repository already knows this: `TacticalVerticalSliceRunner` overrides the sink to 4096 with a comment describing the exact failure, while the `Default` config any real network client would use still ships 256. Zero test coverage.

4. **N-04 (P2).** `Disconnected` is a *droppable* event in the same bounded queue as data events. A dropped disconnect leaks the host-side rate limiter **and** the binder binding for a monotonically-assigned connection id that is never reused — the same permanent `ServerFull` outcome as N-01, reachable without any secret.

**Calibration fact that both prior reports missed:** *nothing in this stack is wired into a player build.* No Runtime code constructs `LiteNetLibCarrier`, `OwnDatagramCarrier`, `ServerTransportHost` or `ClientTransportEndpoint` (grep over `Assets/_GlobalFront/Runtime`: only the declarations match); all 32 `*.Create*` carrier call sites are under `Assets/_GlobalFront/Tests/`. The vertical slice drives the bridge through a **loopback** uplink (`TacticalVerticalSliceRunner.cs:1175–1194`). Every "exploit scenario" below therefore means "once Phase 4 wires this" — which is exactly when it should be fixed, and why none of it is a P0 today.

## 3. Defect Matrix

### N-01 — P1 (Critical) — One socket can own N live sessions; orphaned bindings permanently exhaust the roster and unbind the D-1 guard itself

| | |
|---|---|
| **Files** | `Runtime/Server/Transport/TransportSessionBinder.cs`, `Runtime/Server/Transport/ServerTransportHost.cs` |
| **Lines** | `Bind` 43–84 (unconditional `_tokenByConnection[connectionId] = token;` at **78**); `Release` 100–116 (`_tokenByConnection.Remove(binding.ConnectionId);` at **111**, no token identity check); `HandleReconnectRequest` **322–369** (no ownership guard; `Release`/`Bind` at **339–340**); contrast the D-1 guard at **408–412** and the `MaxPlayers` gate at **414–418** |
| **Symbol** | `TransportSessionBinder.Bind` / `.Release` / `ServerTransportHost.HandleReconnectRequest` |
| **Invariant** | §2.2 "An unauthenticated UDP connection must NEVER hijack, displace, or corrupt existing sessions, players, or rosters"; §2.2 "no leaks of … session tracking structures" |

**Defect.** `Bind` and `Release` are not inverses. `Bind(s, c)` overwrites `c`'s connection mapping without releasing whatever previously owned `c`, so `_byToken`/`_tokenBySession` keep the old binding while `_tokenByConnection` forgets it. `Release(s)` then removes `_tokenByConnection[binding.ConnectionId]` **without checking that the mapped token is the one being released**, so it destroys a mapping belonging to a different session. `HandleReconnectRequest` never calls `TryGetByConnection`, so nothing prevents a second session from being bound to an already-owning socket.

**Reachability — no cryptography is broken and no privileged knowledge is needed.** `TryRebindSession` (`SessionManager.cs:519–612`) requires only that the target session be `SessionState.Disconnected` (**554**), inside the grace window (4000 ticks = **200 s**, `DefaultDisconnectGraceTicks`), and that the caller present the session's own 32-byte secret (**544**, fixed-time compare). An attacker obtains a secret for every session it legitimately creates.

**Failure sequence (two sockets, one attacker):**
1. Socket **Y** handshakes → session **B**, secret `S_B`, player P2. Socket **X** handshakes → session **A**, token `T_A`, player P1. Binder: `_byToken{T_A→A}`, `_tokenByConnection{X→T_A, Y→T_B}`.
2. Y goes silent. `HandleConnectionLost(Y)` → `NotifyConnectionLost(B)` → B is `Disconnected` (grace starts) and `_binder.Release(B)` frees `Y→T_B`. **A is untouched and X is still live.**
3. On socket **X**, the attacker sends `ReconnectRequest(B, S_B)`. `HandleReconnectRequest` performs no ownership check → `TryRebindSession` returns `Accepted` → line 339 `_binder.Release(B)` is a no-op (B is unbound) → line 340 `_binder.Bind(B, …, X)` writes `_tokenByConnection[X] = T_B`, **silently discarding `T_A`**.
4. **Consequence A — dual command authority.** `_byToken` now holds both `{T_A→A(ConnectionId=X), T_B→B(ConnectionId=X)}`. `HandleCommand` (**465–470**) validates `TryGetByToken(token)` plus `binding.ConnectionId == transportEvent.ConnectionId` — both bindings carry `ConnectionId == X`, so the attacker issues commands as **P1 and P2** from one socket. `ValidateCommand` (**651–687**) passes for both: A is still `Connected`, its slot is `Connected`, the match is `Running`. One client now pilots two armies.
5. **Consequence B — duplicate replication streams.** Neither `SessionDetached` nor `OnSessionDetached` ever fires for A, so `ServerReplicationEmitter` keeps A's client slot `Active` and keeps calling `_host.SendSnapshot(A, …)` (`ServerReplicationContracts.cs:94`), which resolves A → `T_A` → `ConnectionId = X`. Socket X receives **two independent snapshot streams** (two `KeyframeSeq` spaces, two tick bases) into one client — for a *legitimate* client that ever reaches this state, the bridge thrashes between keyframe mismatches until the FSM goes terminal.
6. **Consequence C — permanent resource exhaustion.** When X finally drops, `HandleConnectionLost(X)` resolves `_tokenByConnection[X]` → **`T_B` only** → releases B. A's binding survives in `_byToken`, `_tokenBySession` and `_cachedSnapshotTargets` **forever**: no code path releases it (`_binder.Release` is called from exactly three sites — 239, 339, 533 — all of which need either the connection mapping or the token). `BoundCount` therefore never returns to its true value. Repeat the sequence and `BoundCount` reaches `SimulationConstants.MaxPlayers` (**10**), after which line 414 denies every new client with `ServerFull` **for the remaining lifetime of the process**. In parallel each orphan permanently occupies one of the emitter's 10 `ClientState` slots, so once those are exhausted `FindFreeSlot()` returns null and newly attached players are silently never replicated to.
7. **Consequence D — the D-1 guard unbinds itself.** The attacker (which holds `T_A`) sends a graceful `Disconnect` for A. `HandleGracefulDisconnect` (**523–535**) → `_binder.Release(A)` → line 111 removes `_tokenByConnection[X]`, which currently holds **`T_B`** → B's connection attribution is destroyed while B stays bound. `TryGetByConnection(X)` now returns **false**, so the D-1 guard at **408** no longer fires for X, and X may handshake a *further* session. The invariant D-1 was written to enforce is violable by the socket it protects.

**Proof (algebraic).** Let `B₁ = Bind(s₁, c)` and `B₂ = Bind(s₂, c)` with `c` fixed. After `B₂`: `_tokenByConnection[c] = t₂`, `_byToken ⊇ {t₁, t₂}`, `_tokenBySession ⊇ {s₁→t₁, s₂→t₂}`. `Release(s₁)` executes `_tokenByConnection.Remove(c)` — removing `t₂`, which `Release(s₁)` does not own. Hence `connection → token` is non-injective in the *destructive* direction while `token → connection` stays injective: exactly the asymmetry that makes step 7 possible. `BoundCount = _byToken.Count` is monotone non-decreasing under this sequence, and no reachable call decrements it for an orphan.

**Witness status: none.** No test binds two sessions to one connection id; `TransportLifecycleCleanupTests.cs:269–294` is the only direct binder test and asserts `SnapshotTargets` contents plus `ReferenceEquals` only — it never asserts `TryGetByConnection(20)` or `BoundCount` after `Release(s1)`. `BoundCount` is not asserted anywhere in the suite. The connect-path guard *is* witnessed (`TransportFlowAndSecurityTests.ConnectRequest_FromAlreadyBoundConnection_IsDeniedAndRosterPreserved`, :361–415).

**Minimal remediation.**
1. `TransportSessionBinder.Bind`: before writing, reject (return 0 / add a `bool` overload) or release any existing binding that owns `connectionId`. Enforcing "one connection, one session" here makes it structural rather than per-call-site.
2. `TransportSessionBinder.Release`: `_tokenByConnection.Remove(binding.ConnectionId)` only when the mapped token still equals the released token.
3. `ServerTransportHost.HandleReconnectRequest`: mirror line 408 — deny a rebind whose connection already owns a *different* session, and re-check `BoundCount >= MaxPlayers` before `Bind`.
4. Add a `SessionDetached`-equivalent sweep so a session whose binding cannot be resolved by connection is still released (defence in depth for consequence C).
5. Regression tests: (a) rebind of session B on a connection owning session A is denied and A keeps its token; (b) `Release(A)` after a double bind leaves `TryGetByConnection(X)` resolving B; (c) `BoundCount` returns to its pre-exploit value after the socket drops.

### N-02 — P2 (Medium) — The production carrier's C2 receive/reassembly path allocates `2 + N` objects per fragmented snapshot, and its own doc comment says it does not

| | |
|---|---|
| **Files** | `Runtime/Server/Transport/LiteNetLibCarrier.cs`, `Runtime/Server/Transport/FragmentAssembler.cs` |
| **Lines** | `LiteNetLibCarrier.cs` **576–594** (in-place read, correct), **663–743** (receive under `_peerGate`), **696** (`state.Assembler.AddFragment(…)`), **677–681** (the "single allocation" claim + `new byte[payloadLength]`), **572–575** (the second claim), **599** (`reader.GetRemainingBytes()` per C0/C1 message); `FragmentAssembler.cs` **131–138** (`new Group` + `new byte[fragmentCount][]`), **148** (`new byte[length]` per fragment), **167** (`new byte[group.TotalBytes]`) |
| **Symbol** | `LiteNetLibCarrier.HandleSnapshotReceive` → `FragmentAssembler.AddFragment` |
| **Invariant** | §2.1 "No heap allocations on steady-state … receive … or keyframe slice reassembly" |

**Defect.** LiteNetLib's Sequenced channel cannot carry a payload above one packet, so C2 snapshots are application-fragmented (`SendSnapshotFragmented`, 255–344) and reassembled on the receiving side by `FragmentAssembler`. The **send** side was made allocation-free in sprint 2.2 (reusable `_sendScratch` under `_sendGate`). The **receive** side was not: for any message of more than one fragment, `AddFragment` allocates one `Group` class instance, one `byte[fragmentCount][]` jagged array, one `byte[length]` per fragment, and one `byte[TotalBytes]` for the assembled message. The code asserts the opposite twice:

> `LiteNetLibCarrier.cs:572–575` — "the only owned allocation this path makes is the message handed to the event queue (single fragment payload or the fully assembled message)."
> `LiteNetLibCarrier.cs:677–679` — "This is the single allocation of the path." (inside the `fragmentCount == 1` branch, which is the *only* branch where the sentence is true)

**Which process pays.** C2 is server→client, so `HandleSnapshotReceive` runs on the **client's** carrier worker thread — i.e. in the player's own process, the one rendering at 144 Hz under Unity's non-generational Boehm GC. Quantified with the real constants (`MaxDatagramBytes` 1200, `FragmentPayloadBytes` 1171, LiteNetLib's initial MTU 1024 ⇒ `maxChunk ≈ 1000`):

| Payload | Fragments | Objects allocated | Approx. garbage |
|---|---|---|---|
| 500 B delta (≈12 moving units) | 1 | 1 (`new byte[payloadLength]`, :680) | 0.5 KB |
| 4 KB delta (≈100 moving units) | 5 | 1 Group + 1 jagged + 5 slices + 1 message = **8** | ≈8 KB (2× the payload) |
| 16,384 B keyframe slice (409 records) | 17 | **20** | ≈33 KB (2× the payload) |

At the emitter's cadence (up to one delta per client per tick, 20 Hz) a busy match puts roughly **100–160 KB/s** of Gen-0-shaped churn into the client, with 2× amplification on every baseline slice. Rule of thumb the numbers support: **the client allocates about twice the size of every snapshot it receives.**

**Witness status: none, and the existing tests budget the violation.** `LiteNetLibCarrierIntegrationTests` contains exactly one true zero-allocation assertion — `SendFragmentedSnapshots_SteadyState_ZeroHeapAllocations` (:525–656, send path, `measured == 0` over 100 fragmented snapshots, with a positive recorder control at :510–523). The two receive-path tests (:658–710 and :747–796) invoke the private `HandleSnapshotReceive` through a compiled delegate and assert `baseline == 2` then `measured − baseline == 0` — i.e. they *expect and permit* the assembler's allocations and only prove that the latest-wins stale scan adds no extra `List`. `FragmentationTests.cs` (9 tests over `AddFragment`) and `ReliableCarrierTests.cs` (15) contain **no** allocation assertion at all. `TransportPerformanceBaselineTests.cs` measures with `GC.GetAllocatedBytesForCurrentThread()` (:87, :136) and only **prints** it (:170) — a doubly dead number, since the project's own comment at `LiteNetLibCarrierIntegrationTests.cs:513–515` records that this API returns 0 under the editor's Mono.

**Severity note.** `ClientTransportReplicationBridge.cs:178–180` carves the carrier out of *the bridge's* zero-GC claim ("only the transport carrier itself (outside this layer) allocates per datagram"), and `Documentation/CURRENT_STATE.md:35` simultaneously claims the zero-GC hot path of "эмиттера, моста, клиента и транспорта" is validated. ADR-009 contains no allocation clause at all (grep for `zero-gc|allocat|garbage` → no matches). So the carve-out is a code comment, not an accepted decision — and the audit invariant I was given names "receive" and "keyframe slice reassembly" explicitly. Hence P2 rather than P3: it is a real breach of the stated invariant on the shipping carrier, mitigated only by the fact that nothing is wired yet.

**Minimal remediation.** Give `FragmentAssembler` a caller-supplied output buffer and a per-peer preallocated fragment store indexed by `FragmentIndex` (one contiguous `byte[MaxFragmentsPerGroup × FragmentPayloadBytes]` is 2.4 MB — too large; instead one `byte[MaxMessageBytes]`-bounded group buffer per peer sized from the negotiated snapshot bound, ≈16.5 KB, plus an `int[]` of fragment offsets). Keep every existing cap (`MaxFragmentGroups`, `MaxFragmentsPerGroup`, `ReassemblyBudgetBytes`, `EvictUntilBudget`) intact. Then extend the recorder gate to the receive path and **change `baseline == 2` to `baseline == 0`** — the current assertions will otherwise keep passing over a regression. Finally, correct the two doc comments, which are the artifact the next audit round will trust.

### N-03 — P2 (Medium) — Client default REMOVE sink (256) < server REMOVE budget (512): a legal catch-up delta is dropped and mislabelled as peer corruption

| | |
|---|---|
| **Files** | `Runtime/Client/Replication/ClientTransportReplicationBridge.cs`, `Runtime/Server/Replication/ServerReplicationEmitter.cs`, `Runtime/Core/Snapshot/DeltaSnapshotProtocol.cs` |
| **Lines** | bridge **82** (`DefaultRemoveSink = 256`), **68–73** (the contract it violates), **250–252** (sink allocation), **383–393** (`TryDecode` failure ⇒ `_malformedPayloadCount++`, silent drop); emitter **19** (`DefaultRemoveCapacity = 512`), **570–575** (merge), **600–611** (packet-size guard); protocol **52** (`MaxPayloadBytes = 8192`), **71** (`RemoveRecordMinSizeBytes = 2`) |
| **Symbol** | `ClientTransportReplicationBridgeConfig.DefaultRemoveSink` / `ClientTransportReplicationBridge.HandleDelta` |

**Defect.** The bridge documents the rule and then breaks it: *"Decode sinks must never be smaller than the sender's budgets"* (**68–73**). The sender's remove budget is 512; the default sink is 256.

**Arithmetic (verified against the constants, not assumed).** A REMOVE record is `id varint (1–10 B) + cause (1 B)`, minimum 2 B, maximum 11 B. 512 removes therefore encode to between 1,024 B and 5,632 B, plus the 36 B header — always ≤ `MaxPacketBytes` (8,228). So the emitter's own guard at **600–611** passes and the delta *is* sent. The ADD sink is safe (40 B fixed ⇒ ⌊8192/40⌋ = 204 ≤ 256) and the UPDATE sink is exactly safe (2 B min ⇒ 4096 ≤ 4096, **zero margin**). Only REMOVE is inconsistent.

**Failure sequence — reachable in ordinary play, no attacker.** `StreamDeltas` merges the change-sets of every tick in `(baseTick, tick]` (**570**). The per-tick diff engine caps removes at 64 (`ServerSnapshotDiffEngine.DefaultRemoveCapacity = 64`), so a cumulative merge exceeds 256 removes after roughly **5 ticks of heavy casualties** — e.g. a client that hitches, loads, or loses packets for ~250 ms–1 s while ~260 units die in a 1024-unit battle. Then:
1. `DeltaSnapshotWireCodec.TryDecode` hits `removes.Length (256) < header.RemoveCount (≥257)` → `DeltaCodecResult.BufferTooSmall` (:353 region).
2. `HandleDelta` **389–393**: any non-`Ok` result ⇒ `_malformedPayloadCount++` and return. The packet is discarded, **no repair is queued**, the FSM is not told, and a *local configuration fault* is recorded as *peer corruption* — indistinguishable from bit rot in every diagnostic.
3. The server's base advances anyway (`baseTick = Max(LastAckedTick, LastSentTick)`, **564**), so the next delta covers an even wider range and is dropped again.
4. Recovery only when the merge exceeds 512 removes or the 120-tick ring window, at which point `TryMergeRange` fails → `_keyframeFallbackCount++` → `QueueKeyframe` (**570–575**, **608–610**) → a 16 KB multi-slice re-baseline instead of a ~1.5 KB delta. Worst case ≈120 ticks ≈ **6 s** of a client that appears frozen and then hard-resyncs.

**The repository already knows.** `TacticalVerticalSliceRunner.cs:1180–1191` overrides all three sinks to `ClientReplicationWorld.DefaultCapacity` with this comment: *"400 units reaped, spawned or repaired inside a single tick would overflow a 256-entry remove sink, the bridge would call the payload malformed, and the client would quietly stop following the match."* That is a precise description of N-03 — fixed at exactly one call site, while `ClientTransportReplicationBridgeConfig.Default` (what any networked client would take through the 2-argument constructor at **237–240**) still ships the broken 256.

**Witness status: none.** No test decodes >256 removes through the bridge; `DefaultRemoveSink` appears nowhere in the test tree; the largest remove decode anywhere is 16 records at codec level (`DeltaSnapshotWireCodecTests.cs:1240–1275`). The only test referencing the server's 512 (`ReplicationStreamIntegrationTests.cs:222`) passes it to a constructor and asserts nothing about it.

**Minimal remediation.** `public const int DefaultRemoveSink = 512;` (and consider `DefaultAddSink = 512` for symmetry with `DefaultAddCapacity`, since 204 ≤ 256 is only safe while `AddRecordSizeBytes` stays 40). Separately — and more importantly — split the error class in `HandleDelta`: on `BufferTooSmall` call `_receiver.Fsm.ReportBaselineLoss(nowMs)` (or queue a `DeltaResume`) and count it in a dedicated `SinkTooSmallCount`, never in `MalformedPayloadCount`. Add a regression test that pushes 512 removes end-to-end through emitter → codec → bridge and asserts the delta is applied.

### N-04 — P2 (Medium) — `Disconnected` is a droppable event; a dropped one leaks the rate limiter and the binding for a connection id that is never reused

| | |
|---|---|
| **Files** | `Runtime/Server/Transport/LiteNetLibCarrier.cs`, `Runtime/Server/Transport/OwnDatagramCarrier.cs`, `Runtime/Server/Transport/ServerTransportHost.cs` |
| **Lines** | `LiteNetLibCarrier.cs` **843–856** (`EnqueueEvent` drops at `MaxQueuedReceiveEvents` = 4096, `DroppedQueueOverflow++`), **546–551** (the Disconnected event goes through it); `OwnDatagramCarrier.cs` **923–936** (identical); `ServerTransportHost.cs` **202–241** (all host-side cleanup is event-driven), **206** (limiter removal), **210–216** (ack purge), **239** (binder release), **245–249** (`new RateLimiter()` per unseen connection id) |
| **Invariant** | §2.2 "Client disconnection must be O(1)/O(k) clean: no leaks of rate limiters, pending ACKs, or session tracking structures" |

**Defect.** D-5/D-6 made the cleanup correct *and* unconditional within `HandleConnectionLost` — the limiter is removed at **206** before the early return at **218–221**, which is exactly right. But `HandleConnectionLost` only runs if the event survives the queue. Both carriers funnel `Disconnected` through the same bounded FIFO as bulk data, with no priority and no reservation, and silently drop on overflow. Carrier-side state is safe (`OnPeerDisconnected` calls `RemovePeerState` **before** enqueuing, :514–528); **host-side** state is not: `_rateLimiters[connectionId]`, the connection's `_pendingAcks`, the binder binding and the session's roster slot all survive.

**Why it is permanent.** Connection ids are monotonic and never reused (`_nextConnectionId++`, :496 / :579), so a leaked `_rateLimiters` entry can never be overwritten by a later peer, and a leaked binding can never be resolved by connection again — `BoundCount` stays inflated, which is the same terminal `ServerFull` outcome as N-01 step 6, reached without any secret.

**Reachability — quantified, not asserted.** Inbound events per peer are capped by `RateLimiter` at 200 pkt/s (`RateLimitPacketsPerSecond`, `TransportProtocol.cs:197`) and peers by `MaxConnections` = 64, so the worst-case ingress is 12,800 events/s. The host drains the queue completely every `Pump` (20 Hz ⇒ 50 ms), i.e. ≈640 events per interval against a 4096 cap. Overflowing therefore requires the host to stop pumping for **≥320 ms** while all 64 peers sustain their rate limit — a scene load, a GC pause, a debugger break or an alt-tab, not something an external peer can schedule on demand. That is why this is P2 (robustness/availability under load) rather than P1 (on-demand exploit): the consequence is permanent and the trigger is a ordinary host stall, but the trigger is not attacker-controlled.

**Witness status: none.** `DroppedQueueOverflow` is never asserted in any test — it appears only inside `TestContext.Out.WriteLine` (`TransportPerformanceBaselineTests.cs:176`) and failure-diagnostic strings (`ReplicationIntegrationSupport.cs:263, 268`). The nearest bound asserted is `PeakQueueDepth <= MaxQueuedReceiveEvents`, which passes precisely when nothing was dropped.

**Minimal remediation.** Make control events undroppable: either a separate small queue for `Connected`/`Disconnected` drained before the data queue, or reserve headroom (drop *data* events once depth exceeds e.g. 3072 and never drop control). Cheaper alternative that also fixes the class: sweep host-side state against the carrier's live connection set each pump (`PeerMappingCount` / `ConnectionCount` already exist) and purge any `_rateLimiters`/binding whose connection id is no longer live. Add a test that forces `DroppedQueueOverflow` on a `Disconnected` event and asserts `RateLimiterCount` and `BoundCount` still return to 0.

### P3 (Minor) findings

| ID | File / lines | Defect (verified) | Remediation |

The project's own evidence standard is Unity's `GC.Alloc` recorder (`Recorder.Get("GC.Alloc")` + `FilterToCurrentThread()` + `sampleBlockCount`, `LiteNetLibCarrierIntegrationTests.cs:899–921`), with a positive control. That standard is met in the one fixture that uses it. Two other places still measure with `GC.GetAllocatedBytesForCurrentThread()`, which returns 0 under the editor's Mono — `TransportPerformanceBaselineTests.cs:87/136` (printed, never asserted) and `ServerReconnectionTests.cs:197/206/210` (asserted, in a test *named* `ZeroGcAllocations`). See **N-19**. Also note the recorder filters to the current thread, so **worker-thread allocations are invisible to it by construction** — which is precisely why N-02's allocations were never caught: in production they happen on `GlobalFront.LiteNetLib.Receive`, and in the two tests that do reach them the handler is invoked on the test thread with a `baseline == 2` allowance instead of a zero assertion.

**Conclusion.** §2.1 holds for the entire server tick path, the send path of the adopted carrier, and the whole client replication layer above the carrier. It does **not** hold on the adopted carrier's C2 receive/reassembly path, which is the one place the invariant names explicitly ("receive", "keyframe slice reassembly") and the one place no gate measures.

## 6. Concurrency & Thread-Safety Assessment (§2.4)

**Sound:**
- **`TickDriver`** — every mutable field (`_tick`, `_mode`, `_isPaused`) is read and written under `_gate`; `TickDue` is raised outside the lock; the step's index base is captured under the same lock that scheduled it. Single gate ⇒ no lock-order inversion. Witnessed (D-8).
- **`LiteNetLibCarrier`** — the worker thread only enqueues; authoritative processing is host-side. `_peerGate` protects `_connectionToPeer`, `_peerToConnection`, `_peerLimiters`, `_snapshotStates` and `_pendingAdmissions`; `_eventGate` protects the queue; `_sendGate` serialises the shared send scratch. Lock order is consistently `_peerGate → _sendGate` (217→294, 282→294) and never reversed; `_peerGate → _eventGate` in `CloseConnection` (358→372) with no path taking `_eventGate` first. `RemovePeerState` (386–392) removes mapping + limiter + snapshot state atomically, so no map can outlive its peer. `_pendingAdmissions` is keyed by the admitted peer itself, so churn cannot shift capacity accounting (87–93, 488, 521). `_nextConnectionId++` is always inside `_peerGate` (194, 496).
- **`OwnDatagramCarrier`** — single-threaded by construction. Close paths triggered from inside `Pump` defer map removal to `_pendingRemovals` and sweep at the start and end of `Pump` (296, 313, 320–333), so no close path mutates the collection being iterated; `ProcessAcks`/`ProcessTimers` iterate `Unacked` by index and remove from the tail (944–981, 987–1018).
- **Client replication layer** — no cross-thread mutable state: the carrier worker enqueues, the endpoint dequeues and dispatches on the pumping thread, and the bridge, receiver, FSM, world and feedback generator all run on that one thread. No locks are needed and none are taken.
- **`EnvelopeCodec.TryDecode`** (104–174) — every read is bounds-checked against `length` before use (base header 111, fragment header 149, payload 165–169); no out-of-bounds read is reachable from a hostile datagram. This is the strongest-parsed untrusted-input surface in the stack and it is correct.

**Residual concerns:**
1. **`TransportMetrics` counters are non-atomic across the worker/host boundary** (**N-12**) — lost updates on the very counters that would reveal N-04's dropped events or a rate-limit attack.
2. **`HandleSnapshotReceive` performs the whole reassembly while holding `_peerGate`** (663–743), which the host's `Send`/`SendSnapshotFragmented` also need (217, 282). The work is bounded (≤4 groups, ≤2048 fragments) but it is a per-snapshot lock handoff between the worker and the 20 Hz host — a jitter source at 144 Hz, worth measuring once N-02 is fixed.
3. **`peer.GetMaxSinglePacketSize(Sequenced)` is read outside `_peerGate`** (264) while LiteNetLib's MTU-discovery worker may resize the peer MTU. The value only sizes a chunk and is clamped to `FragmentPayloadBytes`, so the worst case is a suboptimal chunk — not a correctness failure. Correctly assessed by the prior report.
4. **`_pendingAdmissions` has no time-based sweep** (93, 838). It relies on LiteNetLib always reporting `OnPeerDisconnected` for an accepted-but-never-connected peer. If that ever does not fire, capacity is consumed permanently — the same failure shape as N-04. Cheap insurance: age entries against `_clock`.
5. **`TransportSessionBinder`, `SessionManager` and `ServerTransportHost` are host-thread-only** and documented as such (`TransportSessionBinder.cs:13–14`, `ServerTransportHost.cs:17–18`). Correct as written; the binder's problem is logical, not racing (**N-01**).
6. **`HandleMessage` is `public`** (`ServerTransportHost.cs:243`) although every production caller reaches it through `Pump`/`HandleEvent`. A public entry point that injects an unvalidated `TransportEvent` into the session gate is an unnecessary surface; make it private (or `internal` for tests).
